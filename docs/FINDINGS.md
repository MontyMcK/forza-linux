## 1. The dump (2026-10-23)

- The archive `forza 2.rar` (RAR5, 39 GiB) holds one top-level folder, `Anthem_1.0.0.64_x64__8wekyb3d8bbwe/`.

  - Verified: read `Mount/AppxManifest.xml`.

## 2. The executable: `Mount/forza_durango_release_final.exe`

- PE32+, AMD64, GUI subsystem.
- ImageBase `0x140000000`, SizeOfImage `0x3A18000` (~58 MB), entry point RVA `0xF18058`.
- Has a `.reloc` section, so it can be relocated, but we should still try to map it at the preferred base.
- Sections: `.text` (0x1DB300F), `BINK`, `RADCODE`, `.rdata`, `.data` (0xAF2568), `.pdata` (0x1F2E28 → full x64 unwind info), `minATL`, `.tls`, `_RDATA`, `BINKDATA`, `BINKCONS`, `RADDATA`, `.rsrc`, `.reloc`.
- **CPU**: plain x86-64 with heavy AVX (VEX-encoded `vmovaps`/`vmulss`…). The Xbox One CPU is AMD Jaguar, so expect at most AVX, F16C, BMI1 and SSE4.2. All of these run natively on Zen, so **no CPU translation is needed**.
  - Verified: `llvm-objdump -d` instruction histogram.
- **TEB/GS usage**: 613 `gs:` references.
  - `gs:0x58` (591×): TEB.ThreadLocalStoragePointer (static `__declspec(thread)` TLS).
  - `gs:0x20` (12×): TEB.NtTib.FiberData. **The game uses fibers.**
  - `gs:0x30` (1×): TEB.Self. `gs:0x10` (1×): StackLimit.
  - So we must point the GS base at a Windows-layout TEB on every thread.
- **RTTI and C++ symbol names are present** (`.?AV...@@` type descriptors). Use them to name classes and vtables.
- **Source paths** are present in assert strings, e.g. `d:\p4\anthem_rc\Engine\App\Src\RenderThread11.cpp`.
- The game is written in C++/CX (WinRT): it imports `vccorlib110.DLL` and starts through `Windows.ApplicationModel.Core.CoreApplication`.

### 2.3 Loader-relevant facts (verified 2026-10-23)

- TLS directory: template 0x150 bytes at rva 0x392e000, `_tls_index` at rva 0x354ebd8, **no TLS callbacks**.
- Load config: security cookie at rva 0x2e68520. 170,286 RUNTIME_FUNCTION entries in `.pdata`.
- The exe has an **export table** of 708 FMOD API functions (`FMOD_System_*`, `?addDSP@ChannelControl@FMOD@@...`), which is handy for naming the audio code.
- The entry point (rva 0xf18058) is the standard MSVC `mainCRTStartup`. It calls `GetSystemTimeAsFileTime` (security cookie), then `__getmainargs`, `_initterm_e`, `_initterm`, then the C++/CX `main`.
- `__chkstk` (rva ~0xf17e7c) reads `gs:0x10` (StackLimit), so StackLimit must be the real lowest stack address.
- Early heap setup: the game reserves 5+ separate 4 GB regions with `VirtualAlloc(type=0x30002000, PAGE_READWRITE)`, i.e. MEM_RESERVE | MEM_LARGE_PAGES | **0x10000000** (an Xbox-only flag, probably graphics/title memory). It then commits inside them with type **0x40000000** (another Xbox flag) plus MEM_COMMIT. Next it installs `XMemSetAllocationHooks(0x141260780, 0x1412608c0)`.
- `TlsAlloc` is imported but `TlsGetValue`/`TlsSetValue` are not. Our TLS slots live in TEB.TlsSlots (0x1480) in case the game reads them inline.
- Startup order observed: `Platform::Details::InitializeData(2)`; static initializers construct `Concurrency::critical_section`s and `concurrent_queue`s and boxed value types; the first `CreateThread` (entry rva 0x30b800, 512 KB stack, CREATE_SUSPENDED, affinity 0x8, priority 2); then main activates `Windows.ApplicationModel.Core.CoreApplication` with ICoreApplication IID {0AACF7A4-5E1D-49DF-8034-FB6A68BC5ED1}.

## 3. Graphics

- The renderer is Direct3D 11.X (Xbox D3D11 with extensions). The source file names end in `11.cpp` (RenderThread11, SkidMarks11, Presentation11).
- **Shaders are standard DXBC, Shader Model 5.** Files `media/shaderpatch/*.durango.vso/.pso` start with the `DXBC` magic and contain only `ISGN`, `OSGN` and `SHEX` chunks. There is no Xbox GCN microcode chunk, so DXVK's DXBC→SPIR-V compiler should handle them as-is.
  - Verified: hex-dumped two sample `.vso`/`.pso` files.
- `.shaderbin` files are a Forza container (magic `burG`, chunks `ECSL`, `SLBD`, `PMBC`, `PMXT`…). They probably wrap DXBC and material bindings **(unverified)**.
- `xg_x` usage means the game computes **tiled texture layouts itself** and probably uploads pre-tiled (GCN tile mode) texture data, or creates placement resources over its own memory. Untiling may be required **(unverified, high priority to check)**.
- **First D3D call** (render thread, rva 0x10d8839 → import thunk 0x19928ce): `D3D11XCreateDeviceX(params, ID3D11DeviceX** dev, ID3D11DeviceContextX** ctx)`. The params struct is on the stack: `+0x00 u32 0x1000B` (probably a version), `+0x04 u32 0x04000000` (flags), `+0x08` 16 bytes of 0, `+0x18 u64 0x3F` (probably a core/affinity mask), `+0x20 u64 0`, `+0x28 u32 0`. It's called right after the game loop's first `CoreDispatcher::ProcessEvents(3)`.
- `D3DMapEsramMemory`: the game places some resources in the 32 MB ESRAM. Emulate it as ordinary GPU memory.
- `EmbeddedXvd/.../d3d11_x.dll` (17 KB) is only a loader: it loads `umd.dll` (or `umd_d`/`umd_v`/`umd_i.dll`, the debug/validation/instrumented builds, all in the same System32) and calls its exports `UMDCreateDevice`, `UMDPresentArray`, `UMDCreateBlob`, `UMDGetDebugInterface`. **`umd.dll` is the real D3D11.X runtime** and our RE reference for every slot (verified: strings and imports of d3d11_x.dll). It has no RTTI, so use `tools/pe_re.py` (vtables / slots / dis / findguid).

### 3.1 D3D11.X object layouts (verified 2026-10-24 in umd.dll + game call sites)

Addresses below are umd.dll RVAs unless they say "game rva".

**The extra base slot.** Every Xbox D3D/DXGI interface has **one extra method right after `SetPrivateDataInterface`** compared to the public SDK. So Xbox slot = desktop slot + 1 from that point on: ID3D11Device from slot 37, IDXGIObject-based from slot 5, ID3D11DeviceChild-based (context, resources…) from slot 7. Evidence: in each vtable, two adjacent slots have the SetPrivateDataInterface shape (GUID, pointer) and every later slot matches the desktop method one position earlier (device: slot 38 returns 0xB100 = GetFeatureLevel, 39 returns a field = GetCreationFlags, 24 and 25 share code = CreateQuery/CreatePredicate, 28 returns E_NOTIMPL = OpenSharedResource, 33 switches on the feature enum = CheckFeatureSupport). What the extra method does is unknown (it uses the same private-data store).

**ID3D11DeviceX**: 84 slots, vtable at 0x16f2e0 (in `.data`), installed by `UMDCreateDevice` (0x2c770). Slots 0–53 = desktop ID3D11Device2 order with the +1 shift from 37 (so 0–54 used). Slots 55–83 are Xbox-only. Slot 55 uses the same function as GetImmediateContext (→ "GetImmediateContextX"). Several Xbox slots return E_NOTIMPL. `src/hle/d3d11x/desktop_slots.h` (generated) has the desktop numbers.
- **Slot 59** (umd 0x2b2b0 → 0x27ed0) creates a 0xA8-byte device child with a **30-slot vtable at 0x16f580**: `(const desc*, out**)`. Desc: `+0 u32` flags whose low 4 bits pick an engine (the game passes 1 and 2), `+4 u32` ring size (game 0x10000, 0 means 0x80000), `+8 u32` 0. The game creates two at game rva 0x10d8afb / 0x10d8b3d and keeps them at renderer+0x120 / +0x128. The object's slot 8 returns 2, slots 19–25 take 64-bit GPU virtual addresses and reject anything ≥ 1<<40. **Probably the DMA/copy-engine contexts (name unverified).** This is the first unimplemented slot the game hits.

**IDXGIDevice (Xbox)**: 18 slots at 0x16f6c0 = desktop IDXGIDevice2 (17) + the extra slot 5. Slot 8 = GetAdapter (the game calls it at game rva 0x10d8980). Slots 9–17 return DXGI_ERROR_UNSUPPORTED (0x887A0004). IDXGIAdapter slot 8 = EnumOutputs (game passes `(0, &out)` at game rva 0x10d89a2, keeps the output at renderer+0x28).

**Xbox-only IIDs** (umd QueryInterface returns the object itself for each):
- `{88671610-712E-4F1E-84AB-01B5948BD373}` on the device (umd 0x28627). We call it ID3D11DeviceX. The game QIs for it and keeps it at renderer+0x18, then calls slot 59 on it.
- `{9458FE06-C78D-47F7-96A0-EC7B727BE1E9}` on the context (umd context QI 0x8c33, checked first): probably ID3D11DeviceContextX.
- `{48800095-7134-4BE7-9186-B86BECB26477}` on the context (umd generic QI 0x336f). Identity unknown. The game keeps it at renderer+0x30 and does not null-check it.

**The immediate context is a memory block the game pokes directly.**
- umd's context constructor (0x266e0 / 0x267f0) **copies the 0x828-byte (261-slot) method table from 0xd6950 into the context at +0x3D0** and sets the context's vptr to context+0x3D0. (The vtable scanner shows the source as 253 slots: the last 8 entries aren't code pointers.) It also stores 1 at +0x8. AddRef/Release forward to the device's refcount through the device pointer at +0x10.
- **The game inlines context methods.** 54 inlined sites read the byte at **context+0x390**: if **bit 1** is set they call through the embedded table (`call [ctx + 0x3D0 + 8*slot]`), otherwise they write state into the block themselves. Example, game rva 0xc56060: IASetInputLayout inline stores the layout at ctx+0x178 and ORs 0x89 into ctx+0x168 (the dirty flags), or calls ctx+0x460 = slot 18. umd's slot 18 does the same writes.
- **Some inlined writes are not guarded by the bit**: e.g. game rva 0xc5b74e, 0x10c3fa6, 0x10de370 store a packed 64-bit value (0x3FFC0009E00 / 0x9FFC0009E00) at ctx+0x170 and OR 0x46 into ctx+0x168. Our draw code will have to read those fields. Meaning unknown.
- **Context slot map (verified across all 261 slots in umd, 2026-10-24):** 0–6 IUnknown/DeviceChild like desktop, **7 = the extra base slot**, **8–24 = desktop 7–23 (+1)**, **desktop 24 IASetPrimitiveTopology has NO slot** (the game always inlines it, see below), **25–143 = desktop 25–143 exactly** (checked e.g. 83 IAGetPrimitiveTopology writes a dword, 72/77/81/100/104/109 have the constant-buffer-getter shape, 112/113 GetType/GetContextFlags return 0, 114 FinishCommandList E_NOTIMPL on the immediate context, 115/116 reuse the CopySubresourceRegion/UpdateSubresource code). **144–260 are Xbox-only.** `ctx_slot()` in d3d11x.h encodes this. Exception: **slot 20 (index buffer) has an Xbox signature** `(this, hw index type (0 = 16-bit, 1 = 32-bit), buffer, offset)`.
- **The inlined IASetPrimitiveTopology** stores `table[topology]` (a u64) at ctx+0x170 and ORs 0x46 into ctx+0x168, where `table` is a 65-entry u64 array in the game image at **game rva 0x1df87e0** (bits 41+ = GCN primitive type). We read that table at run time to map the value back (context.cpp `apply_inline_state`, called before every draw).
- **Byte ctx+0x390 has two mode bits the inlined code checks:** bit 1 (55 sites): inlined state setters call the table instead of writing fields. **Bit 0 (37 sites): the game writes raw command-buffer packets itself** at ctx+0x50 (write pointer, limit +0x58, slot 208 = "make room"); with bit 0 set it instead calls **slot 209 with compact commands**: `u32 header` (bit 31 bind, bits 28–30 kind 0 SRV / 1 CB / 2 sampler, bits 16–19 stage 0 VS 1 HS 2 DS 3 GS 4 PS 5 CS, bits 8–15 first slot, bits 0–7 count 1..32) followed by count × {`u64 object`, `u64 extra`}; header & 0x0fff0000 == 0x01060000 with kind 1 binds vertex buffers with extra = stride << 48 | offset (Azimuth's decoder, its rva 0x1cbc80); other kinds have extra 0. ### 3.2 Texture layouts (xg_x) and tiling (verified 2026-10-24)

- **Assets are stored pre-tiled.** `.swatchbin` textures (`burG` container: `BCXT`/`HCXT` chunks; header at +0x40: u16 width, height, depth, …, u8 mip count, format code) decode to scrambled 128-pixel column blocks as linear data.
- **The console GPU tiling:** GB_TILE_MODE0–31 and GB_MACROTILE_MODE0–15 tables at xg_x.dll rva 0x16648 / 0x166c8 (standard GCN 1.1 4-pipe P4_16x16 values; listed in src/hle/xg/gcn.cpp), pipe interleave 256 B and DRAM row 2 KB (xg code at rva 0x6559/0x6560). With AMD addrlib (Mesa, MIT) configured this way (`GB_ADDR_CONFIG = 0x10001002`, family CI), our layouts match the console's XG **exactly** for real assets (tests/gcn_layout_test.cpp: 4/4 sizes, incl. full mip chains — every level is padded to a power of two), and the untiler turns a real BC4 texture into the correct image (tools/swatch_view.cpp).
- **XGComputeOptimalTileMode** (xg rva 0x12f0 → 0x4140), reimplemented in xg.cpp: buffers 0x1F, depth binds → -1, 1D → 8 (linear aligned), 3D → 13, 2D with MiscFlags bit 27 → 16/17 (PRT), else 14 if width/height reach a minimum from a 7-entry table (rva 0x14b58) indexed by log2(min(clamp(2·bpe·64, 256, 2048), bpe·64·samples)) − 6, otherwise 13. **XGComputeOptimalDepthStencilTileModes**: depth = stencil = {1 sample: 0, 2/4: 1, 8: 2}.
- **XG_TEXTURE2D_DESC** = Xbox D3D11 desc (0x34) + TileMode + Pitch (1D/3D the same pattern). **XG_RESOURCE_LAYOUT** is 0xd40 bytes: u64 size, u64 alignment, u32 mips, u32 planes, 3 × 0x460-byte planes {u32 usage, u64 size, u64 base offset, u64 alignment, u32 bytes per element @+0x20, 15 × 0x48-byte mips {u64 size, u64 offset @+8, u64 slice size @+0x10, pitch px, pitch bytes @+0x1c, …, width/height/depth in elements @+0x30/34/38, samples, tile mode}}. Evidence: xg's GetResourceLayout copies 0xd40 bytes; xg's methods read +0x08, +0x30–0x38, plane+0x20; the game's untile loop (rva 0x10c3860) uses the same fields. The XG "texture address computer" is NOT COM: 0 AddRef, 1 Release, 2 GetResourceLayout, 3 GetMipLevelOffsetBytes(plane, mip), 4 GetTexelElementOffsetBytes(plane, mip, x, y, z, sample) (vtable rva 0x14670).
- **Plane usages and metadata planes (2026-10-26, xg_x 2D builder rva 0x1770, DB setup rva 0x59c0, plane finaliser rva 0x2600; decompiled in research/private/xg_decomp):** usage 1 colour/default, 2 CMASK, 3 FMASK, **4 HTILE**, 5/6 the two planes of a two-plane format not bound as depth, **7 depth, 8 stencil**. A 2D texture with 1 mip and bind DEPTH_STENCIL (and not RENDER_TARGET) gets [HTILE] DEPTH [STENCIL]: HTILE unless misc bits 20 and 21 are both set (no depth / no stencil compression, our names), alignment 0x800, size = 4 bytes per 8×8 tile of the padded surface after aligning it to 128×64 (one slice of ≤ 2M pixels) or 512×512, rounded up to 16 KiB. A 1-mip RENDER_TARGET gets colour + CMASK (+ FMASK with MSAA), **not modelled yet** (STUB). Each plane's base offset is the previous plane's *unaligned* end; the running end is aligned to the plane's alignment before adding its size; layout size = final end. The game reads usage 4 and 7 planes to DMA-clear depth targets (rva 0x1150044 stores offset/size; rva 0x1131b85 fills HTILE with 0xffffffff and depth with 1.0f). Our old layout (usage 2 for depth, no HTILE) left those fields unset and the game filled 0xff000000 bytes over thread stacks.
- **Streamed textures:** the game reserves a whole mipmapped texture (VirtualAlloc type 0x30002000) and commits only the tail holding the small mips (e.g. 0x160000 reserved, top 0x60000 committed), clamping LOD until the big mips stream in. Uploads must skip uncommitted mips (placement.cpp, gpumem::readable).


### 3.3 Unified memory (our design)

Placement resources live in game memory; DXVK resources don't. `src/hle/d3d11x/gpumem.*` tracks writes with userfaultfd async write-protect + `PAGEMAP_SCAN` (the Linux GetWriteWatch). Binding a placement resource uploads it if written since the last upload (buffers: UpdateSubresource; textures: untile each mip/slice); `begin_upload` re-arms its pages first. Render targets/depth/UAVs are GPU-owned and never uploaded. Map on a placement buffer returns the game memory itself.

- **Pages are shared (2026-10-26):** tracking is per 4 KiB page, and the game packs small placement buffers (constant buffers of 0x120 B, …) next to each other. Re-arming one resource's pages also cleared the written state of its neighbours, whose new contents then never uploaded (`FL_CHECK_TRACKING=1` hashes every "clean" resource against its last upload and logs `MISSED write`). placement.cpp keeps a page → resources index; when `begin_upload` re-arms written pages, every other resource on them gets `force_dirty`.
- **No SRV/RTV/UAV hazard unbinding on Xbox (2026-10-27):** the game's lighting probes are built at load: 256x256 R11G11B10 cubes (rendered), their mip chain by its own compute shader (8x8 groups, one dispatch per face and mip) that reads mip N-1 through a whole-resource SRV (t0) while writing mip N through a UAV, then a pixel shader convolves mip 3 with a 256x256 R32F weight table into 32x32 R32G32B32A32 cubes, copied into 32x32 R11G11B10 probes that a compute shader blends every frame into the irradiance cube (scene t0). D3D11/DXVK unbind an SRV that overlaps a bound UAV, so t0 read zeros, all mips were black, the probes black and every shadowed surface pure black. DXVK patch 0003 makes SRVs never hazardous (TestHazards() = false). Baked probes (BC6H placement cubes, tile mode 13) are decoded by a PS that samples face cb1.x / mip cb1.y (written per draw with Map DISCARD) — they were fine.
- **Bundle inheritance remaps (2026-10-27):** context slots 156-159 = Remap{ConstantBuffer,ShaderResource,Sampler,VertexBuffer}Inheritance(stage, slot, src stage, src slot), stages in compact-command order (0 VS, 1 HS, 2 DS, 3 GS, 4 PS, 5 CS); Azimuth checks CB slots < 14, SRV < 128 (rva 0x12c0c0 / 0x12c230), records packet kind 0xc, and at replay binds the executing context's binding of (src stage, src slot) as it was when the bundle started into (stage, slot) (rva 0x1c98f0). ~210k remaps while the world loads, all in bundles and **between draws** ("after N draws"): the executing context binds each object's textures/constants to its **CS** slots, the bundle remaps them per draw: PS t16-t23 <- CS t2-t9, PS t13/t14 <- PS t13/t14, CB VS/PS 5/6/9/12 <- CS CB 0-8. Ignoring them made every bundled material sample whatever the executing context had bound (scrambled terrain/road). Implemented in DXVK (tools/dxvk-patches/0002): a remap closes the bundle's current CS chunk and is applied, from the executing context's D3D11 state, before the next chunk replays.
- **Bundles do not bind render targets (2026-10-27):** the game records track and car bundles with 1x1 dummy targets bound (R11G11B10 colour, D32S8 depth: the formats of the real targets, which the console needs to build pipelines); the draws must go to whatever the executing context has bound. Azimuth's bundle OMSetRenderTargets (rva 0x12a3c0 → 0x128390) validates and stores the views as shadow state only and records no command; its OMSetRenderTargetsAndUnorderedAccessViews (rva 0x12a500) records only the UAV part (packet kind 0xd). We do the same (ContextX::bundle). Before this, every road, terrain and car draw went into the 1x1 dummy (pipeline statistics: 2.7M pixel-shader invocations, nothing on screen) and the world-edge box showed through.
- **Write-tracking cost and the frame scan (2026-10-27):** in gameplay the game executes ~356 command lists per frame (bundles), each re-syncing ~12 placement resources, plus ~6800 placement binds per frame: ~15000 PAGEMAP_SCANs, ~4.7 ms per frame (FL_LOG=fps). Linux fact used by the fix: `PAGEMAP_SCAN` with `PM_SCAN_WP_MATCHING` but without `PM_SCAN_CHECK_WPASYNC` silently skips VMAs that are not registered for async WP (fs/proc/task_mmu.c `pagemap_scan_test_walk`), so one ioctl can walk from the lowest to the highest tracked address. Walking all ~GBs of tracked memory takes ~3 ms, so each frame walks a quarter of it. Only ~500 pages per frame are written while driving, and ~95% of syncs are of resources not written for 10+ frames.
- **MSAA resolve needs FMASK (2026-10-27):** the scene renders into a 4x MSAA R11G11B10 target (game rva 0x10cadc5, MiscFlags 0x40000) and is resolved by a full-screen pixel shader (fs.6209bcf0) that reads, besides the samples, an R8_UINT view of the same target: on the console that is its **FMASK**, 2 bits per sample naming the colour fragment it uses. 0 = all samples are fragment 0: copy sample 0. Otherwise each fragment is weighted by its sample count (nibbles of 1 << 4·fragment) in a tonemapped blend. D3D11 refuses the cross-format view, so we back it with a stand-in texture (resources.cpp); a zeroed one made every pixel "one fragment", so nothing was anti-aliased and alpha-to-coverage foliage showed as a checkerboard. DXVK stores every sample, so the stand-in now holds the identity map (0xe4 at 4x, 0x2 at 2x). `FL_FMASK_ZERO=1` brings back the zeros (A/B screenshots: grass dithering and stair-stepped car edges vs smooth).
- **Motion-blur car mask: HTILE buffer and stencil in R (2026-10-27):** the car is kept sharp by a per-pixel mask: compute shader cs.17a22aed (dispatch 240x135, 8x8 groups) writes `stencil & 127` of the main MSAA depth target (D32S8, placement tile mode 1) into a 1920x1080 R8_UINT texture that the motion-vector pass reads; cs.7f4c20de does the same plus a per-pixel depth output. Both first read the depth target's **HTILE** through a 128 KiB raw buffer the game creates at rva 0x10c9594 (MiscFlags 0x20020: raw views + Xbox bit 0x20000, no init data, nothing ever copies into it; R32 raw SRV of 0x8000 dwords): per 8x8 tile, bits 0-3 Z mask (0 = cleared: write the clear depth, 15 = fetch every pixel, else decode plane equations) and bits 8-9 stencil state (0 = no stencil: mask 0, 1 = one fetch per tile, 2-3 = fetch every pixel). DXVK has no HTILE, so the buffer read as zeros: every tile "cleared, no stencil", the mask was 0 everywhere and the car blurred with the background. Fix 1: buffers with MiscFlags 0x20000 are created filled with 0xffffffff (the expanded state the game's own DMA clears write), so both shaders take their exact per-pixel paths (resources.cpp, STUB). Fix 2: the shader reads stencil from **.x** of an X32_TYPELESS_G8X24_UINT view; desktop D3D11 (and DXVK) put it only in G, so .x read 0. DXVK patch 0005 returns it in R and G (R is undefined for these formats on desktop). The car pixels carry stencil 2 (DSS stencil REPLACE ref 2 before the car's bundles). Azimuth keeps a "D3D12 HTILE pattern buffer" (rva 0x1c2bc0: a pattern-filled buffer per 32-bit value, rounded to 1 MiB, copied into GPU memory for DMA fills).
- **Bundle sets must never be filtered as redundant (2026-10-27):** DXVK skips a state set that matches the state it tracks for the context (e.g. `if (m_state.ps != shader)`). A bundle's deferred context starts from the reset state, so a set to the default inside a bundle (the car's depth-only shadow bundles call PSSetShader(nullptr)) recorded nothing, and at replay the bundle ran with the executing context's state: the pixel shader of the last object the static-cascade pass drew. On the frame that updates the 2048² static cascade (1 frame in 4; the cascades t111-t114 update round-robin), that leftover shader discards the car (its textures, CS t3-t6, are unbound that frame: the restore=FALSE command list at the end of each frame resets the context, and the 2048² pass binds only CS t0-t2), so the dynamic shadow map t108 had no car and its shadow vanished every 4th frame. Which shader is left over depends on what was drawn last, hence "only in some places". Found with FL_TRACE_ECL_STATE=1 (full state at each traced ExecuteCommandList) and FL_TRACE_BUNDLES=1 (record-time state: "PS none"). Fixed in tools/dxvk-patches/0004: bundle contexts record every set (21 setters). Verified on 16 consecutive frames: the car shadow is in every frame (FL_ECL_NULL_PS, a one-off experiment that unbound the PS before each bundle, gave the same result).
- **Performance: bundles and DXVK's flush/restore logic (2026-10-27):** measured with the new tools (FL_GPU_PROFILE / FL_GPU_PROFILE_AT_TIME: GPU timestamps around every operation of a frame, summed per render target; FL_CPU_PROFILE=<start>:<len>: SIGPROF sampling per thread and function; FL_LOG=fps now prints DXVK's own counters through patch 0006). In dynamic mode on Monty's save (RX 9070 XT, driving): (1) **~600 queue submissions and ~600 render passes per frame**. DXVK submits after every few CS chunks, and a bundle replay is dozens of chunks (one per inheritance remap, ~10-13k chunks per frame); every submission also ends the render pass, reloading and storing the 4x MSAA colour + depth. Patch 0007 leaves bundle chunks out of the chunk-count heuristic: 40-50 submits and 65-80 render passes per frame, GPU frame 7-15 ms -> 3.9 ms (main pass 4-7 ms -> 2 ms). (2) **`placement_containing` scanned every placement for each DMA fill**: 20% of all CPU samples; GPU-owned placements are now in an address-ordered map. (3) **A full state restore after every bundle**: each bundle ended with DXVK's ResetCommandListState (unbind everything) and the executing context then re-bound all of its state (all six stages up to the highest slot used, PS SRVs up to t116), ~380 times a frame. Patch 0008 records what a bundle binds (and its remap targets) and restores only that; the trailing reset is dropped for bundles. The render thread is the limit (100% of a core per /proc CPU time); open-world frame rate went ~90 -> ~175 fps (5 min soak: 153-193 fps average, 1% low ~80-90, no crash). (Tried and dropped: synchroniseUpdateToRenderThread off + unlockframerate on via the settings constructor, rva 0xf696c5 / 0xf694c2: slower, 87-97 fps, and exposed the unmap race below.)
- **Duplicate state objects (crash, 2026-10-27):** DXVK returns its existing object for a blend / depth-stencil / rasterizer / sampler description it has seen (like D3D11, which returns the same interface). We made a second wrapper for it, which took over the registry entry; releasing it erased the entry while the first wrapper was still in use, and the next OMGetDepthStencilState aborted ("DXVK returned object ... that has no wrapper", Monty's crash at 66 s). Creating a state object now hands back the live wrapper (acquire_wrapper: a reference only if its count is above 0), and a getter that still finds an unwrapped state object (released while bound) gets a fresh wrapper of the right type (wrap_orphan_state).
- **CoreApplication GPU policy (2026-10-27):** CoreApplication statics interface {42A6A529-3CC6-4867-B5B7-6D1FAF5325F9}: S+0 get / S+1 put of a bool (the console's Kinect GPU reservation switch; Azimuth's CoreApplication object implements "ApplicationGpuPolicy" and holds this IID). The game sets it around movies and cinematics and at the end of an event (rva 0x1101950); when the activation failed it raised a Platform::Exception there (rva 0x11019a1, caught further up), skipping the rest of that code: Monty finished a mission and the game never registered it. Now implemented (the value is kept).
- **Uploads raced with VirtualFree (2026-10-27):** a streamed texture's memory was decommitted (VirtualFree MEM_DECOMMIT, remapped PROT_NONE) by another game thread while the render thread untiled it: SIGSEGV in gcn untile_rows on a ---p page. Placement uploads now hold gpumem::read_guard() (shared) while reading game memory; VirtualFree (release and decommit) and XMemFree take unmap_guard() (exclusive) first.
- **Bundles bake bindings in:** a draw bundle (deferred context, flag bit 0x20000) is recorded once and executed every frame. Uploading a placement resource while recording puts that upload into the command list, so replays use stale data. Deferred contexts now only record which placement resources they bind; ExecuteCommandList syncs them (on the executing context) before running the list.

- **FMOD Studio** is statically linked (FMOD C++ symbols in the exe). Banks are `media/audio/**/*.bank`, RIFF `FEV ` format (740 files).
- **FMOD output (verified 2026-10-25):** `MediaDevice::GetDefaultAudioRenderId` (IMediaDeviceStatics S+4, game rva 0x1a62690) → `ActivateAudioInterfaceAsync(id, IID_IAudioClient2, null, handler, &op)` (rva 0x1a62910) → waits for the handler, `op->GetActivateResult` (slot 3), QI for IAudioClient2. - **XMA through SHAPE (AcpHal, verified 2026-10-25 from AcpHal.dll + FMOD's code at rva 0x19d47a0/0x19d4f40):**
  - `ApuCreateHeap(cached bytes, non-cached bytes)` (game: 5 MB, 256 KB); `ApuAlloc(void** va, u32* apu, size, align, flags)` flags 1 = cached heap, 2 = non-cached; `ApuMapVirtualAddress(va) -> u32`, `ApuMapApuAddress(u32) -> va`, `ApuIsVirtualAddressValid(va, access)`.
  - `AcpHalAllocateShapeContexts(SHAPE_CONTEXTS*)`, 0x60 bytes: six counts (SRC, EQ/comp, filter/volume, DMA, XMA, PCM), six array pointers, six APU addresses. Element sizes 32/160/32/16/64/32; XMA ≤ 0x200, PCM ≤ 0xE00, others ≤ 0x1000; numSrc must equal numXma + numPcm. FMOD asks for 512 SRC, 1024 DMA, 512 XMA.
  - `AcpHalCreate(IAcpHal**)`. IAcpHal (not COM): 0 Connect(cmd entries, msg entries), 1 Disconnect, 2 SubmitCommand(type 1..0x1b, u64 context, u32 id, const void* payload, u32 arg), 3 PopMessage(24-byte msg) -> bool, 4 GetNumMessages, 5 Release, 6–9 return 0x8AC80F0E, 10 deleting dtor. Commands are 256-byte queue records; payload sizes per type: 1/0x15–0x1b 16 B, 2/3/5/7 4 B, 4 none, 6/8 64 B, 9–0xe 12 B, 0xf–0x12 8 B, 0x13 24 B, 0x14 112 B.
  - FMOD's protocol: command 2 = message mask (FMOD sends 0xfe); command 1 = run a SHAPE flowgraph `{u32 numCommands, u32 flowgraphApu, u64}`; FMOD keeps 4 credits and gets one back per **message type 2** (flowgraph done). Message 0x10 carries a 64-bit frame counter; 4/8/0x20/0x40/0x80 are errors it logs.
  - Our ACP (src/hle/acphal/acphal.cpp) runs one flowgraph per 128-sample frame and acknowledges it, but doesn't execute SHAPE commands yet (XMA voices are silent). Azimuth decodes XMA with a modified FFmpeg (its licenses.txt).

- **SHAPE protocol (2026-10-27, from Azimuth's checks: ACP command processor rva 0x1400bd1c0, input update 0x1401a31c0, flowgraph executor 0x1401a3680, XMA voice 0x1401a27c0 / packets 0x1401a2eb0):** commands: 1 flowgraph {u32 opcodes, u32 APU address, u64 0} (queued, one per 128-sample frame), 2/3 message mask set/clear, 5/6 XMA start (index / 512-bit mask), 7/8 XMA stop, 0x10 DMA consumption {u32 dma, u32 blocks}, 0x13 XMA input update {xma, buffer 0/1, packets, set packets, set pointer, APU pointer} (sets the buffer's valid bit). `id` = scheduled frame (FMOD: 0xffffffff), `arg` = notification mode (0). A command with a non-zero 64-bit context posts message 0x10 {+8 type, +0xc context, +0x14 frame}. Flowgraph opcodes (u64, low 5 bits): 1 allocate a 128-float mix buffer ((u>>33)&0x1fff); 2 SRC of context (u>>13)&0xfff from its XMA voice into mix buffers (u>>25)&0x1fff and, stereo, (u>>38)&0x1fff; 0x10 DMA mix buffer (u>>14)&0x1fff into DMA context (u>>27)&0xfff. After a graph: message 2 {+8 graph APU}, frame counter +1; a starved SRC posts message 4 {+8 SRC index, +0xc graph}. **XMA context = the Xbox 360 XMA context layout** (64 bytes; w0 packets/valid bits 20-21, w1 stereo bit 29 / sample rate bits 27-28 (24/32/44.1/48 kHz) / output valid bit 31, w2 read offset in bits (packet<<14 | 0x20), w4 bit 31 current buffer, w5/w6 buffer APU addresses, 2048-byte packets consumed whole). SRC context (32 B): w1 rate (0x40000 = 1.0) + state bits 22-23 (1 = XMA voice), w2 input samples consumed, w3 phase (18 bits), w4 target rate. DMA context (16 B): w1 read block bits 0-4, write block 8-12, full bit 16; w2 ring APU address; w3 blocks-1 and format 0x100 (128 floats per block, one channel). Implemented in src/hle/acphal/shape.cpp: with it FMOD's streams load and the intro runs without any override (the FL_BREAK_RETURN workaround is obsolete).
- **SHAPE scheduling and FMOD (2026-10-27, measured with FL_LOG=audio):** FMOD builds every flowgraph in ONE APU buffer and queues several graph commands ahead. The hardware must run (or copy) a graph when it is submitted; Azimuth's "audio processor" thread (rva 0x1400bd5c0) runs commands as they arrive, with no clock of its own. FMOD paces itself: it submits a graph when its rings need data (~2x the 128-sample frame rate) and includes a voice in a graph only when that voice's 4-block DMA ring has room (~half of the graphs). When we ran graphs on our own 375/s clock, up to 3 stayed queued, FMOD's view of the rings was stale, and each voice ran in ~1/3 of the graphs: sounds played at ~0.36x speed with gaps. FMOD then cut them off; 995 stops in 90 s, all with input still queued. Recorded output: ~40 clicks/s while loading and in gameplay; running commands on submit brings it to 0.4 (loading) and 4.3 (gameplay). acphal.cpp also copies a graph's opcodes at submit.
- **FFmpeg's XMA decoder holds samples back (2026-10-27):** wmaprodec.c `xma_decode_packet` keeps 4096 samples in its per-stream FIFO until end of file (`nb_samples -= FFMIN(nb_samples, 4096)`, for multi-stream alignment), trims 64 at the start, and skips the first frame (`s->skip_frame = 1`). A hardware voice never reaches end of file, so every sound lost its last 5184 samples (measured over 12 voices: expected frames x 512 from the packet headers, the top 6 bits of each packet's big-endian header, minus decoded = 5184 each). tools/ffmpeg-xma-patches/0001 outputs single-stream frames as they are decoded and keeps the first frame. Azimuth's licence notice describes the same change to its FFmpeg 8.1.3.
- **XMA voices are mostly short one-shots:** ~18 per second start in gameplay, all with loop count 0 (no hardware loops), mono or stereo at 48 kHz, 1-25 packets.
- **WASAPI buffer vs PipeWire:** FMOD asks for 20 ms (960 frames) and writes 480-frame blocks per event. PipeWire's default quantum here was 1024 frames, so a 960-frame buffer ran dry on every pull (a 64-frame gap every 1024 frames). With the device period at ~480 frames (SDL hint), two device clocks against our 10 ms events still emptied it ~12 times a second. wasapi.cpp now reports max(requested, 4 device periods) and signals every 5 ms.
- **The intro waits for FMOD streams (2026-10-26):** media/stateflow.zip holds the game's state flows (XML). `free_roam_start_ie.xml` `hero_car_flow` plays Anthem_Tone_Video, then `wait_for_cutscene_loaded` (jetty_transition) → wait_for_streaming → wait_for_loading_complete → IE_opening.bk2 → … → `global.fade_in`. States::WaitForCutsceneLoaded (vtable rva 0x2d34ce0, update rva 0x978da0) needs FUN rva 0x4da470 (load state +0x314 == 4) and 0x4da3b0 → 0x1746710 → 0x17468f0 → Cinematic3DObject children ready (rva 0x1746a70); the cutscene's **CinematicAudioEvent** (rva 0x17469a0) waits for each entry: AudioObjectOneShotFmod ready flag (+0xb0 = `EventInstance::getStreamLoadingState` (rva 0x1a98a30) == 3, set at rva 0x100d580/0x100d3f0) and IAudioDialogPlayer::DialogStatus state (+0x24) past 0/1/2. - FMOD exports only the low-level API; Studio functions are found by their error-name strings ("EventInstance::getStreamLoadingState" etc.).

## 5a. C++ runtime layouts (verified from game code)

- `Concurrency::concurrent_queue<T>` base `_Concurrent_queue_base_v4`: `{vfptr, rep*, items_per_page @0x10, item_size @0x18}`. The derived vtable is `0 _Move_item(page&, idx, src)`, `1 _Copy_item`, `2 _Assign_and_destroy_item(dst, page&, idx)`, `3 scalar deleting dtor`, `4 _Allocate_page()`, `5 _Deallocate_page(page*)`. A page is a 16-byte header followed by items (`item = page + 16 + idx*item_size`). Verified by disassembling the vtable at rva 0x2c66210.
- **PPL tasks (from the reference msvcr110, 2026-10-25):** `_RefCounter {vfptr: 0 deleting dtor, 1 _Destroy; long refs @8}`. `_CancellationTokenState`: state flag @+0x10 (0 none, 1 canceling, 2 canceled; inlined `_IsCanceled` reads it), allocated 0x80 by `_NewTokenState`; `(token*)2` is `_None()`. `_AsyncTaskCollection` 0xf8 with the `_TaskCollection` at +0x10 (the inlined `_ScheduleWithAutoInline` calls `_Schedule/_RunAndWait/_Cancel` on this+0x10 and `_Reference()`s first; the collection's completion does the matching `_Release()`). `_UnrealizedChore`: vfptr (0 = deleting dtor), TaskProc @+8, owning collection @+0x10 (scheduling twice is an error), chore wrapper @+0x18, runtime-owns-lifetime byte @+0x20. ConcRT runs chores inside a catch-all; we do the same with `seh::guarded_call`.
- **Cancellation registrations hold initialRefs + 1 references** (2026-10-28, reference msvcr110): `_RegisterCallback(TaskProc, data, initialRefs)` (0x180001ae8) allocates 0x48 bytes, stores initialRefs at +8, and the inner `_RegisterCallback(registration*)` (0x180001a34) adds the list's own (`lock add [reg+8], 1`). `_Invoke` (0x180001ccc) CASes the state 0 -> thread id, runs the callback unless that fails, and always drops the list's reference. Every call site in the exe and in Microsoft.Xbox.Services.dll passes initialRefs = 1 and, when the task goes away, calls `_DeregisterCallback` and then releases its own reference inline (`lock dec [reg+8]`, vfptr[1] at zero; e.g. Services 0x18001ca73). Services.dll registers two such tasks every 30 s while offline (an Xbox Live poll). Our token_register used to count the list's reference inside initialRefs, so deregister freed the registration and the caller's `lock dec` wrote into freed heap; after 84 min one hit a smallbin link (`free(): chunks in smallbin corrupted`, bk off by one, the stale registration still showing token/state 2/callback 0x180017600 in the core). tests/concrt_token_test.cpp checks the counts.
- **C++/CX exceptions carry their dynamic type** (reference msvcr110 `_CxxThrowException` rva 0x47458, vccorlib110 `Exception(int)` rva 0x18088 / `COMException(int)` rva 0x18470): a ThrowInfo with attribute 0x10 (TI_IsWinRT) is only the hat's static type; the real ThrowInfo is in the object's WINRTEXCEPTIONINFO, embedded at object+0x20 (hr +0x40, ThrowInfo +0x50, size 0x40 at +0x58) and pointed to by the word at object−8; `_CxxThrowException` reads `(*(obj−8))+0x30`. `Heap::AllocateException(n)` allocates n+0x10 and returns +0x10 (rva 0x1aa4c). PPL's `_RethrowUserException` (game rva 0x305c70) throws through a `Platform::Exception^` variable, so without this rule `catch (COMException^)` never matches.
- C++/CX boxed values: the ctor stores `GetIBoxVtable(this)` / `GetIBoxArrayVtable(this)` at `this+8`, replacing the compiler's IPropertyValue vtable (seen at rva 0x1986b98).
- **x64 C++ EH (FH3): a catch funclet's first bytes map to the try's state, not the catch's** (2026-10-27). Microsoft.Xbox.Services.dll rva 0x29850 (a 0x32-byte PPL task-handle invoke: one try, try 0..0, catch_high 2, 4 catches; FuncInfo rva 0x285180) has IP map `0x1f2824 -> 0, 0x1f2831 -> 1`: the funclet at 0x1f2824 is state 0 for its prolog and state 1 for its body. That funclet calls rva 0x17490 (stores the exception in the task) and rethrows (`throw;`, call at 0x1f2846). A dispatcher that takes the running catch's state from the funclet's first byte matches the same try block again, catches its own rethrow, and recurses ~14 KB per level until the 2 MB thread stack overflows (the 41 s / 615 s crashes; each level logs one "PPL task's exception was never observed"). The catch's own state is `try_high + 1` (cxx_eh.cpp run_catch).

## 5b. Memory, audio and misc facts (2026-10-25)

- **XMemAlloc attributes** (decoded by the game's own error message at rva 0x125d850): dwObjectType bits 0–13, dwPageSize bits 14–15, dwAllocatorId bits 16–23, dwAlignment bits 24–28, dwMemoryType bits 29–32.
- The game's `operator new` (rva 0x3229c0) allocates from per-category heaps; the category is the u16 at TLS+0x124 (0x902 = audio), and a budget table at rva 0x354fe10+0x10a070 (0x28 per category, enforced when byte +0x10a3f6 has bit 4) can refuse fallback allocations.
- **`mmdevapi!SetWasapiThreadAffinityMask(mask)` returns the previous mask** (the process mask the first time), 0 + ERROR_INVALID_PARAMETER for a mask outside the process's (reference MMDevAPI.dll rva 0x81f0). FMOD's WASAPI output treats 0 as failure; the game then replaces AudioEngineFmod (vtable rva 0x2e73898) with the silent AudioEngineCommon (0x2e733e0, chosen in rva 0x140f68fb0 when slot 0 Init fails), whose slot 84 returns an empty shared_ptr that the world load dereferences (rva 0x100f896).
- IPackageTransferManager S+0 (IIterable<uint32> chunks, enum): install-order request; fully installed → S_OK (game rva 0x11d0b1a).
- Context slots 156–159 (Remap*Inheritance) are `ret 0` in umd: no-ops.
- XG `Slice2DSizeBytes` of a 3D texture is one depth slice (addrlib's `sliceSize` is the whole level): the game fills its 8×8×16 R8G8 linear (tile 8) colour LUT by `z × Slice2DSizeBytes` (rva 0x13b38c0).
- **Install chunks and the title screen (2026-10-25).** The game keeps a set of installed chunks (rva 0x36613f0) fed by `IsChunkInstalled` answers (rva 0x11d0370), `AreChunksInstalled` (rva 0x11cf000) and the whole-package PackageTransferWatcher's **ChunkCompleted** events (handler rva 0x11ceaa0 reads `args.ChunkId`, IChunkCompletedEventArgs {C1B7DCCE-…} S+0). The FMOD bank loader `AudioContentBankFmod::Load` (rva 0x1012110) only consults that set (rva 0x11d0470) for the chunk `CFileSys` maps the bank to (slot 36, rva 0x11f3fe0): `MasterBank.bank` → chunk 0x6df, `MasterBank.strings.bank` 0x6e9, radio Tracks 0x711/0x71b… Chunk 0 means "no chunk" in the file-open paths (rva 0x11e7cb0/0x11f6780/0x11f9960 skip it). The package's chunk list is in `Mount/hash.manifest`: 12-byte records from offset 8, first u32 = chunk id, ids ≥ 0x3fffffff aren't content chunks (1394 chunks; Azimuth builds its set this way). We report every listed chunk as completed when the game subscribes to a whole-package watcher (it does at ~0.5 s); without that no bank loads.
- **Why the title waited:** after the logo parade the title (rva 0x1413250) starts only when the `Splash` (vtable rva 0x2e533c8) slot 154 returns its "finished" byte (+0x44c). That byte is set by the Splash's audio-event handler (rva 0xe93140, event 0x10/4) when the mixer snapshot **`BASE_PressStartMusic`** (/MasterMixer/Snapshots/BaseSnapshots, AudioSnapshotInfo.xml) reports started, which needs MasterBank. With the silent AudioEngineCommon the event is answered at once.
- **Context slot 154 InsertFence(flags) → u64** (game rva 0x1131b65 tracks it at rva 0x10cedb0); we return a counter.
- **DMA engine context** (device slot 59 object, umd vtable 0x16f580). Azimuth's vtable filler (rva 0x101650, interface 6) fills exactly slots 3, 8, 9, 10, 16, 17, 18, 19, 22, 24, so those are the ones the game uses. 9 CopyResource(dst, src, flags 0), 10 CopySubresourceRegion(desktop args + flags 0) (Azimuth strings "DMA CopyResource flags=" etc.), 19 WriteStatus(u64 address, 4-aligned): writes the u32 HRESULT of the last LZ decompression ("DMA status"), **24 LZDecompressMemory(dst, src, u32 src_bytes, u32 flags 0)**: the source is a **zlib stream** (Azimuth rva 0x1483a0 checks the RFC 1950 header, inflates bytes 2..n-4 with libdeflate and compares the big-endian Adler-32; status 0, 0x8007000D bad data, 0x80070017 checksum); output length comes from the stream. 25 = 24 with mode 1 in umd (unused). 16 InsertFence(flags) → u64 (umd 0x8f8d0 gets the fence via 0x8e2c0 and kicks off via 0x8e380 unless flags bit 0; the game's call returns to rva 0x1131bcc, just after the fill), 17 InsertWaitOnFence(flags, u64 fence) (fence bits 48–55 = engine), 18 kickoff (HRESULT), 21 CopyMemoryToMemory(dst, src, bytes), 22 FillMemoryWithValue(dst, bytes, u32) in dwords, 24/25 decompression variants, 26 writes a 3-dword packet 0x20d with an address (unidentified). GPU address = CPU address of title memory, so we run copies/fills synchronously on the CPU (skipping GPU-only memory the CPU never committed); Azimuth names them DmaCopy/DmaFill/DmaDecompression.
- **DMA fills clear the placement shadow maps (2026-10-26):** in gameplay the render thread issues six fills per frame: HTILE planes with 0xffffffff and the depth planes (D32, R32_TYPELESS) with 1.0f of three gpu-owned placement depth textures (1536×1536 at +0x24000 after its 0x24000 HTILE, and two 1024×1024 at +0x10000). They are the shadow maps the scene shaders read in t108–t110. A fill over a GPU-owned plane must become a GPU clear (dma.cpp `fill_gpu_owned`); without it every shadow test fails and the whole world is shadowed. LZDecompressMemory: ~4500 calls in the first minute of gameplay, all status 0, from two streaming threads.
- **SetShaderResourceViewMinLOD (context slot 223, umd 0x17e60 → 0x57e10):** min LOD = max(lod, view's first mip) (view dimension at view+0x94, first mip at +0x98), stored as 4.8 fixed point (×256, saturated at 0xfff) in T# word 1 bits 8–19 (view+0x64). It counts resource mips. The game calls it ~1300 times in the first minute of gameplay with clamps of 1–4 on streamed BC textures (tile mode 14): the texture streamer keeps the GPU off mips that have not arrived.
- The game uses the D3D immediate context from more than one thread (render thread draws while the main thread clears/copies; `FL_LOG=ctxthreads`). On Azimuth, immediate-context calls from any thread append to one call stream applied by a worker; we turn on DXVK's per-call lock (ID3D10Multithread).

- **Device slots 60/61** (Azimuth names): IsFencePending(u64 fence) / IsResourcePending(resource) → BOOL; the game spins on them (rva 0x10d7dda after DMA LZ work, rva 0x114fee9). **Context slot 240** SetResourceCompression(resource, flags): umd 0x17ec0 rewrites DCC/HTILE enables; the game passes 0 while loading (rva 0x11420a3); a no-op for us.
- **Deferred contexts as draw bundles (2026-10-26):** the game creates deferred contexts with flags 0x60000 and 0xa0000; Azimuth (rva 0x128ff0) accepts only 0, 0x60000, 0xa0000 and treats **bit 17 (0x20000) as a draw bundle** (separate vtable, rva 0x102690). Executing a bundle (rva 0x12c540) requires restore=FALSE and replays it on the executing context's current state: bundles **inherit** render targets, viewports etc. The game's 3D frame (≈870 draws, most in bundles) sets no render target or viewport inside the bundles (trace: viewport 0x0), so on DXVK's plain deferred contexts nothing is rasterised: the 3D scene after the intro is black. Implemented 2026-10-26 by a DXVK patch (below).
- **Bundle inheritance on DXVK (2026-10-26):** with the bundle patch (tools/dxvk-patches) the game's ~600 bundles per frame run on the immediate context's state; the main pass executes them with RT0 + RT1 (1920x1080 R11G11B10) and a D16 depth bound by the immediate context. Bundles are recorded once and replayed (none are recorded in a steady-state frame).
- **ESRAM fields:** the two u32 after the desktop D3D11 descriptor (CreateTexture2D/Buffer) are the ESRAM offset and an ESRAM byte budget (e.g. 1920x1080 tonemap target 0x0+0x800000, scene 0xdd0000+0x800000, depth 0x17e0000+0x820000; small targets use 0x1000000 budgets larger than themselves). Many targets share offsets (time-aliased). We ignore them: each is its own DXVK texture.
- **Post-processing chain (frame trace, 2026-10-26):** MSAA forward/sky pass → resolve/composite into ESRAM 0xdd0000 (bright) → compute luminance (60x34 tiles, 1x1 average ≈ 0.56) and 480x270 downsample → depth-based 480x270 chain and bloom pyramid (black) → 16³ LUT build (compute 2x2x16) → tonemap (PS: motion blur from t3/t6, car layer `color*t9+t8` gated by D16 t10 and main depth t11, bloom add, exposure = VS TexCoord1.w = exp2(lerp of cb1 c6 by luminance between c5 thresholds + c3.w), filmic curve from cb1 c2/c4 divided by its white value, LUT with cb1 c552 = (1/32, 15/16, enable), vignette c8-c13) → copy to the back buffer. Full-screen passes use a 3-vertex buffer (pos float4 + uv float2) with the default rasterizer state.
- **Movies:** after the title the game plays media/UI/Videos/Anthem_Tone_Video.bk2 (195 MB, ~75 s); press_start.bk2 is the title background, T10_MS_Combined.bk2 the boot logos.

## 6. Azimuth vs us: why theirs runs (2026-10-25)

Read from Azimuth's strings and decompiles (Rule 1: behaviour only). Its stack: D3D11.X → Azimuth's own D3D12 layer → D3D12 / vkd3d-proton → Vulkan ("graphics vkd3d-proton shader cache …").

| Area | Azimuth | Us |
|---|---|---|
| Title graphics memory | One contiguous reservation of placeholders (`VirtualAlloc2` + `MapViewOfFile3` over a section), so the memory can be opened as a GPU heap; tracks commits/releases ("a release of title memory", "withdraw the heaps over title memory") | Plain mmap/heap memory; XMemAllocDefault now gets dedicated mappings (was the C heap) |
| Placement buffers | **Zero copy**: `ID3D12Device3::OpenExistingHeapFromAddress` (device slot 48, rva 0x1401504d0) opens a D3D12 heap over the game's memory and places the buffer in it ("D3D12 heap/buffer over title memory"). CPU writes reach the GPU and GPU writes reach the CPU, like an Xbox | A separate DXVK buffer, copied on bind when page tracking says dirty; GPU writes never come back to the CPU |
| Change detection for what must be copied (tiled textures) | OS **write watch** (`GetWriteWatch`, "WriteSeal/WriteUnseal"); if the host refuses, **compare contents** before uploading ("placement uploads compare contents", rva 0x140121930) | Since 2026-10-25 the same idea: userfaultfd write-protect in async mode + `PAGEMAP_SCAN` (gpumem.cpp; works unprivileged with UFFD_USER_MODE_ONLY). Replaced the mprotect + SIGSEGV hook, whose EFAULT/race/decommit problems caused most of that day's crashes |
| ESRAM | Real shared backing; `D3DMapEsramMemory` maps views of it, so aliased mappings of the same pages see the same data | Pages made RW, aliasing ignored |
| Audio | Executes SHAPE flowgraphs (SRC, XMA, DMA…), decodes **XMA2 with a pinned FFmpeg** ("Pinned FFmpeg lacks XMA2 decoder") | Flowgraphs acknowledged, nothing executed: XMA voices are silent and never progress |
| Immediate context | Calls from any thread append to one call stream, applied by a worker thread | DXVK per-call lock |
| Offline Live | Token requests fail with 0x800704CF; privilege checks Restricted; offline secure template from the manifest | Same (since 2026-10-25), no SecureDeviceAssociationTemplate yet |

Linux equivalents of the two big missing pieces: **VK_EXT_external_memory_host** (RADV supports it; vkd3d-proton uses it to implement `OpenExistingHeapFromAddress`) gives zero-copy GPU access to the game's memory; **userfaultfd write-protect in async mode + `PAGEMAP_SCAN`** (the kernel interface Wine uses for `GetWriteWatch`), or content comparison, replaces the mprotect fault hook.

## 6c. Frame timing (2026-10-27)

- **The game presents with sync interval 2** (DXGIXPresentArray sync 2 flags 0x14, then Present(2)): one frame per two 59.94 Hz vblanks. Its update steps a fixed time per frame, so on a 260 Hz monitor (interval 2 = 130 fps) it ran ~4x too fast. Our Present now waits on a virtual 60 Hz vblank clock (dxgi.cpp `pace_present`; MangoHud measured 29.5 fps average). The user confirms the speed is right at 30 fps; uncapped is too fast.
- **The update step** is computed at game rva 0xf58770 (called once per update, writes the step to `this+0x64`): `dt = min(clock(this+0x68).elapsed, 0.2f)` (0.2 at rva 0x1dfc288), clamped at >= 0. If setting `+0x25f1` is on, dt = 1/59.94 (rva 0x1ffe244). If setting `+0x2dab` is on, dt = 1/29.97 (rva 0x1ffe248), loaded by the 8-byte `vmovss` at rva 0xf587df after the `je` at rva 0xf587dd (bytes `74 1e`). The settings object comes from rva 0x295940.
- **These are named engine options**, registered at rva 0xf6dd60 through the option parser at rva 0x10805a0 (`name` or `name=true|1` sets true, any other value sets false): `synchroniseUpdateToRenderThread` (+0x2dab, default 1 from the constructor at rva 0xf696c5), `lockupdatetimeto60fps` (+0x25f1), `unlockframerate` (+0x25f2). With synchronise off and unlockframerate off, the game calls a limiter at rva 0xf74c53 (`obj->vtable[0xf8]` when +0x25f4 == 1).
- **Where the options come from is still open** (no longer needed for dynamic mode, see below). The retail game does not parse argv: with argv `unlockframerate`, breakpoints on rva 0x299950, 0xf6dd60 and 0x10805a0 never hit, and the fixed-step branch (0xf587df) runs. The game never opens `.\cmdline.txt` (the path is built by CCommandLineParameters' constructor, rva 0x107c340 with prefix `.\`; `loadcmdlinedottxt=<path>` and `ignorecmdlinedottxt` are options too). Leads: the "CommandLine" string, CForzaCommandLineParameters (constructor rva 0x283480), and what calls rva 0x299950 (no direct caller, probably a vtable). Azimuth's real-time mode patches the `je` at 0xf587dd into `jmp` ("synchronised update step branch"), and its 60 fps mode points the load at 0xf587df at the 1/59.94 constant ("synchronised update step load"). It also patches a "UI step"/"UI clock tick" (the UI clock advances a fixed step per frame) and has a "GPU value wait loop" site. (Facts from the game's own code; Azimuth only told us which sites matter.)
- **Dynamic frame rate works (2026-10-27):** `FL_FRAME_PACING=dynamic` patches the `je` at rva 0xf587dd into `jmp` at load (src/loader/game_patches.cpp, bytes checked first), so the update step is the measured frame time (clamped to 0.2 s) while the render/update sync stays on. The UI clock needs nothing more: its tick (rva 0x142c5e0, a vtable method at 0x2ecfbf8) takes the update's dt in xmm1 and steps `min(dt × scale(+0x80), 1/30)`; FL_BREAK_XMM showed 0.0333667 every frame at 30 fps and 0.0097-0.013 at ~100 fps. (Azimuth's fixed 60 fps mode rewrites that site to a 1/60 constant because its step stays fixed.) Measured: RT from a standstill with screenshots every 0.5 s of real time (FL_SCREENSHOT_AT_TIME): dynamic at ~95 fps and capped at 60 read the same speeds (6/23/35/52/62/68 mph at 63/64.5/66/68/70/71 s); console mode trails slightly because it ran at 27-30 fps there and its fixed step slows the game when frames drop. Uncapped, the loading screen presented ~15000 fps and loading stalled, so dynamic mode paces to FL_FPS_CAP or, by default, the display's refresh rate. Monty's machine, 4x MSAA: menus at the cap, open world ~88-92 fps (GPU ~85%, MangoHud).
- The render thread (rva 0xf9a340) renders when the update has published a new frame (counter `+0xb8` of the object at `this+0x198`, bumped at rva 0x108181d / 0x108193e) and stores the renderer's present interval (vtable +0x1f8, 1 or 2) in the global at rva 0x2eb7074. The main-loop frame tick is rva 0xfa78a0; its clock at `this+0xc8` gives the frame time (`+0x360`) and an FPS counter (`+0x358`). The game never calls IDXGIOutput::WaitForVBlank or IDXGISwapChain::GetFrameStatistics (FL_TRACE_TIME=1 counts these and the QueryPerformanceCounter callers).

### 7.2 Memory (payload context, 2026-10-30)
- **Page size 16 KiB** (`sysconf`, `getpagesize`). `sceKernelMprotect(base+4K, 4K, R)` returns 0 and protects the **whole 16 KiB page** (a write to base+0 faults). So PE sections sharing a 16 KiB page need the union of their protections.
- **Executable memory:** `mmap(RWX)` of anonymous memory is *granted but silently without execute* (`sceKernelQueryMemoryProtection` reports 0x3). Map RW, then `sceKernelMprotect` to RX or RWX: code runs (flexible and direct memory). RWX lets code be rewritten without another protection change. libc `mprotect(RX)` also returned 0. `sceKernelMapDirectMemory` with RWX is refused (0x80020016).
- **Reservations:** `sceKernelReserveVirtualRange(&a, len, 0x10 /*fixed*/, 64K)` gave 512 MiB exactly at **0x140000000** (the game's image base) and 16 GiB exactly at 0x1000000000. Anonymous `mmap(MAP_FIXED)` inside a reservation works; a fixed *file* mapping inside a reservation read the file correctly here (prospero-win reports it breaking in a title: recheck there). A reservation with no address landed at 0x200020000.
- **`MAP_FIXED|MAP_EXCL` replaces an existing mapping** (the old page read 0 afterwards). There is no Linux `MAP_FIXED_NOREPLACE` equivalent: the loader must keep its own bookkeeping of what it mapped.
- Direct memory: `sceKernelGetDirectMemorySize()` = 0 and `AvailableDirectMemorySize` = 0x8002000c in a payload, yet `sceKernelAllocateDirectMemory(64 KiB, type 12)` succeeded (phys 0x2000430000) and mapped RW at a fixed address inside a reservation; 1 GiB was refused (0x80020023). A payload has no direct budget of its own (PS5_PayloadSDK fork notes the same); the title run decides this.
- Flexible memory in a payload: configured 8192 MiB, available 8158 MiB; `mmap(NULL, 4 GiB, PROT_NONE)` and `mmap(NULL, 512 MiB, RW)` were both granted. Titles are reported to get ~448 MiB flexible (unverified here).

### 7.3 Threads, sync, signals (payload context, 2026-10-30)
- **GS base:** `sysarch(AMD64_SET_GSBASE=131)` sets it, `AMD64_GET_GSBASE=130` and `mov %gs:0` read it back; it is per thread and survives sleeps, yields and syscalls. Initial value 0. A signal handler runs with the interrupted thread's GS base (read with sysarch inside the handler). Whether the ucontext holds it is unverified: the value was not at FreeBSD's `mc_gsbase` slot (+808); the copy found at +1160 is probably the test's own local variable above the signal frame.
- **umtx** replaces futex: `_umtx_op(addr, UMTX_OP_WAIT_UINT_PRIVATE=15, expected, NULL, &relative_timespec)` / `UMTX_OP_WAKE_PRIVATE=16` (and the shared 11/3) wake in 50.1 ms as scheduled; a changed value returns at once; a 30 ms timeout returns -1/ETIMEDOUT(60) after 30.1 ms.
- **Signal context (FreeBSD layout, offset by 48 bytes):** `uc_mcontext` at **ucontext+64**; inside it the FreeBSD amd64 order: rdi +8, rsi +16, rdx +24, rcx +32, r8 +40, r9 +48, rax +56, rbx +64, rbp +72, r10..r15 +80..+120, **rip +160** (ucontext+224). The **FXSAVE image is at ucontext+320** (xmm0 at +480, MXCSR at +344). Measured with markers in every GPR and xmm0-15.
- Faults: a read of a PROT_NONE page gives SIGSEGV with the right `si_addr`; returning after moving rip resumes. A write to a read-only page gives **SIGSEGV** (not SIGBUS); a handler that `sceKernelMprotect`s the page RW and returns lets the write land: 640/640, **~41 us per fault + mprotect** (GPU write tracking cost). int3 gives SIGTRAP with rip after it; ud2 gives SIGILL with rip on it. `sigaltstack` + `SA_ONSTACK` delivers on the alternate stack.
- **MXCSR at process start is 0x9fc0** (flush-to-zero and denormals-are-zero on). Windows and Linux start at 0x1f80: game threads must be given 0x1f80 explicitly.
- Default pthread stack **64 KiB**: every thread we create needs an explicit stack size.

### 7.6 Compiling Windows-ABI code for the PS5 (2026-10-30)
- clang's `x86_64-sie-ps5` target rejects `__attribute__((ms_abi))` ("calling convention is not supported for this target"), which every HLE export and vtable uses (WINAPI).
- `-target x86_64-unknown-freebsd9` accepts it and emits the Windows x64 convention (args in rcx, rdx, r8, r9, the fifth at [rsp+0x30 from rbp's frame]); such an object, built against the PS5 SDK headers, links into a title with tools/ps5/link_title.sh next to PS5-target objects (checked 2026-10-30, not run yet).
- Predefined macros that differ from the PS5 target (clang -dM -E): wchar_t is 16-bit on the PS5 (use `-fshort-wchar`), `__PROSPERO__`/`__SCE__` (define them), `__FreeBSD__` 9 (target freebsd9), `__BIGGEST_ALIGNMENT__` 32 vs 16 (watch max_align_t / aligned new), PIC level 2 (`-fPIC`), no `__float128` on the PS5. Flags to keep from PS5_Vulkan's prospero-clang18: `-fno-stack-protector -fno-plt -femulated-tls -fdenormal-fp-math=ieee -march=znver2`.

### 7.7 First runtime run on the PS5 (M1, 2026-10-30)

### 7.10 thread_local destructors (2026-10-31)
- Everything the PS5 build compiles uses **emulated TLS** (`__emutls_v.*`, `__emutls_get_address`): each thread's thread_locals are heap blocks that emutls frees from a pthread key destructor. C++ thread_local destructors run from another pthread key destructor (the SDK fork's `ps5___cxa_thread_atexit_impl`, platform/src/cxa.c). The emutls one ran first, so `~shared_ptr` of kernelx's `thread_local std::shared_ptr<Thread> t_self` read freed memory at thread exit: two short-lived game threads crashed at once at 4.8 s (rip in `__release_shared`, garbage control-block pointer, r12/r13 in libkernel) during a burst of ~30 thread starts. Fix: no thread_local of ours has a destructor (t_self is a plain pointer to a heap shared_ptr freed at thread end; trace.cpp's string is a char buffer), and `tools/ps5/build.sh runtime` refuses objects that import `__cxa_thread_atexit`. DXVK's and RADV's archives import none.

### 7.13 What things cost in a PS5 title (os_test COST lines, 2026-10-31)
| | Linux (Monty's PC) | PS5 title |
| --- | --- | --- |
| `clock_gettime(CLOCK_MONOTONIC)` | 15 ns | **877 ns** |
| `mprotect`, 1 or 16 pages | 0.33 / 0.14 us | **28.5 / 28.9 us** |
| shared_mutex lock_shared + unlock | 8 ns | 32 ns |
| thread_local increment (emutls on the PS5) | 0.6 ns | 0.3 ns |
- Consequences: page-protection write tracking is ~90x dearer than on Linux (each re-arm and each write fault pays an mprotect), and every clock read ~60x. Remapped memory is checked (`Resource::remapped`, set by the remap hook) before such a buffer is read again.
- **Result in game (2026-10-31): 30 fps** (291 of 296 frames at 32 ms), 3609 draws per frame, GPU idle ~29 ms per frame; placement: 3.0M syncs per 10 s (746 ms comparing/scanning), 52.6k uploads (56 ms), re-arm 33 ms. Linux with FL_COMPARE_BELOW=16384 in game: 30 fps, no errors.

### 7.14 Memory and stutter fixes (2026-10-31)
- **Decommit returned nothing** on the PS5: pages were zeroed and protected page by page (two mprotects, ~57 us per 16 KiB; 64 MiB took ~230 ms) and their direct memory stayed allocated until the whole reservation was released. The game streams by decommitting inside its regions (12 GiB + 4x4 GiB), so our backing could only grow. Now whole 64 KiB units are unbacked (a fixed `sceKernelReserveVirtualRange` over them replaces the mapping, then `sceKernelReleaseDirectMemory` of that part; blocks are split) and partial units are cleared one run per call. Console os_test: decommitting 16 pages of 32 returns the memory and they commit again as zero.
- **Address space never reused:** address-less reservations only climbed (`g_next_anywhere`), so every large heap block (>= 512 KiB) and freed region used new space toward the 1 TiB a title may use. They now wrap around to 64 GiB.
- **Watched ranges outlived their memory:** `os::write_watch_unregister` drops (or trims) ranges on decommit/release (gpumem::notify_remap), as userfaultfd does with the mapping on Linux.
- A commit that only maps fresh read/write units skips its final mprotect (28 us).
- FL_LOG=fps now logs per hitch what that frame did (commits, frees, file reads/opens, write faults, uploads, new threads, new pipelines: common/perf.h) and every 10 s a memory line (our direct memory and blocks, largest free block, flexible memory, handles by type, watched ranges, placed resources) to spot leaks. On Linux at the title: 2174 handles (424 files, 1257 semaphores, 449 events).
