## 1. The dump (2026-10-23)

- The archive `forza 2.rar` (RAR5, 39 GiB) holds one top-level folder, `Anthem_1.0.0.64_x64__8wekyb3d8bbwe/`.
  - "Anthem" is FH2's internal codename (source paths say `d:\p4\anthem_rc\...`). `8wekyb3d8bbwe` is Microsoft's publisher ID. This is not EA's Anthem.
- `Mount/` holds the **decrypted** title package: the game exe, `AppxManifest.xml`, the `media/` assets (~2400 files) and a few DLLs.

  - Verified: read `Mount/AppxManifest.xml`.

## 2. The executable: `Mount/forza_durango_release_final.exe`

- PE32+, AMD64, GUI subsystem, 58,204,160 bytes on disk.
- ImageBase `0x140000000`, SizeOfImage `0x3A18000` (~58 MB), entry point RVA `0xF18058`.
- Has a `.reloc` section, so it can be relocated, but we should still try to map it at the preferred base.
- Sections: `.text` (0x1DB300F), `BINK`, `RADCODE`, `.rdata`, `.data` (0xAF2568), `.pdata` (0x1F2E28 → full x64 unwind info), `minATL`, `.tls`, `_RDATA`, `BINKDATA`, `BINKCONS`, `RADDATA`, `.rsrc`, `.reloc`.
- **CPU**: plain x86-64 with heavy AVX (VEX-encoded `vmovaps`/`vmulss`…). The Xbox One CPU is AMD Jaguar, so expect at most AVX, F16C, BMI1 and SSE4.2. All of these run natively on Zen, so **no CPU translation is needed**.
  - Verified: `llvm-objdump -d` instruction histogram.
- **TEB/GS usage**: 613 `gs:` references.
  - `gs:0x58` (591×): TEB.ThreadLocalStoragePointer (static `__declspec(thread)` TLS).
  - `gs:0x20` (12×): TEB.NtTib.FiberData. **The game uses fibers.**
  - `gs:0x30` (1×): TEB.Self. `gs:0x10` (1×): StackLimit.
  - So we must point the GS base at a Windows-layout TEB on every thread.
- **RTTI and C++ symbol names are present** (`.?AV...@@` type descriptors). Use them to name classes and vtables.
- **Source paths** are present in assert strings, e.g. `d:\p4\anthem_rc\Engine\App\Src\RenderThread11.cpp`.
- The game is written in C++/CX (WinRT): it imports `vccorlib110.DLL` and starts through `Windows.ApplicationModel.Core.CoreApplication`.

### 2.3 Loader-relevant facts (verified 2026-10-23)

- TLS directory: template 0x150 bytes at rva 0x392e000, `_tls_index` at rva 0x354ebd8, **no TLS callbacks**.
- Load config: security cookie at rva 0x2e68520. 170,286 RUNTIME_FUNCTION entries in `.pdata`.
- The exe has an **export table** of 708 FMOD API functions (`FMOD_System_*`, `?addDSP@ChannelControl@FMOD@@...`), which is handy for naming the audio code.
- The entry point (rva 0xf18058) is the standard MSVC `mainCRTStartup`. It calls `GetSystemTimeAsFileTime` (security cookie), then `__getmainargs`, `_initterm_e`, `_initterm`, then the C++/CX `main`.
- `__chkstk` (rva ~0xf17e7c) reads `gs:0x10` (StackLimit), so StackLimit must be the real lowest stack address.
- Early heap setup: the game reserves 5+ separate 4 GB regions with `VirtualAlloc(type=0x30002000, PAGE_READWRITE)`, i.e. MEM_RESERVE | MEM_LARGE_PAGES | **0x10000000** (an Xbox-only flag, probably graphics/title memory). It then commits inside them with type **0x40000000** (another Xbox flag) plus MEM_COMMIT. Next it installs `XMemSetAllocationHooks(0x141260780, 0x1412608c0)`.
- `TlsAlloc` is imported but `TlsGetValue`/`TlsSetValue` are not. Our TLS slots live in TEB.TlsSlots (0x1480) in case the game reads them inline.
- Startup order observed: `Platform::Details::InitializeData(2)`; static initializers construct `Concurrency::critical_section`s and `concurrent_queue`s and boxed value types; the first `CreateThread` (entry rva 0x30b800, 512 KB stack, CREATE_SUSPENDED, affinity 0x8, priority 2); then main activates `Windows.ApplicationModel.Core.CoreApplication` with ICoreApplication IID {0AACF7A4-5E1D-49DF-8034-FB6A68BC5ED1}.

## 3. Graphics

- The renderer is Direct3D 11.X (Xbox D3D11 with extensions). The source file names end in `11.cpp` (RenderThread11, SkidMarks11, Presentation11).
- **Shaders are standard DXBC, Shader Model 5.** Files `media/shaderpatch/*.durango.vso/.pso` start with the `DXBC` magic and contain only `ISGN`, `OSGN` and `SHEX` chunks. There is no Xbox GCN microcode chunk, so DXVK's DXBC→SPIR-V compiler should handle them as-is.
  - Verified: hex-dumped two sample `.vso`/`.pso` files.
- `.shaderbin` files are a Forza container (magic `burG`, chunks `ECSL`, `SLBD`, `PMBC`, `PMXT`…). They probably wrap DXBC and material bindings **(unverified)**.
- `xg_x` usage means the game computes **tiled texture layouts itself** and probably uploads pre-tiled (GCN tile mode) texture data, or creates placement resources over its own memory. Untiling may be required **(unverified, high priority to check)**.
- **First D3D call** (render thread, rva 0x10d8839 → import thunk 0x19928ce): `D3D11XCreateDeviceX(params, ID3D11DeviceX** dev, ID3D11DeviceContextX** ctx)`. The params struct is on the stack: `+0x00 u32 0x1000B` (probably a version), `+0x04 u32 0x04000000` (flags), `+0x08` 16 bytes of 0, `+0x18 u64 0x3F` (probably a core/affinity mask), `+0x20 u64 0`, `+0x28 u32 0`. It's called right after the game loop's first `CoreDispatcher::ProcessEvents(3)`.
- `D3DMapEsramMemory`: the game places some resources in the 32 MB ESRAM. Emulate it as ordinary GPU memory.
- `EmbeddedXvd/.../d3d11_x.dll` (17 KB) is only a loader: it loads `umd.dll` (or `umd_d`/`umd_v`/`umd_i.dll`, the debug/validation/instrumented builds, all in the same System32) and calls its exports `UMDCreateDevice`, `UMDPresentArray`, `UMDCreateBlob`, `UMDGetDebugInterface`. **`umd.dll` is the real D3D11.X runtime** and our RE reference for every slot (verified: strings and imports of d3d11_x.dll). It has no RTTI, so use `tools/pe_re.py` (vtables / slots / dis / findguid).

### 3.1 D3D11.X object layouts (verified 2026-10-24 in umd.dll + game call sites)

Addresses below are umd.dll RVAs unless they say "game rva".

**The extra base slot.** Every Xbox D3D/DXGI interface has **one extra method right after `SetPrivateDataInterface`** compared to the public SDK. So Xbox slot = desktop slot + 1 from that point on: ID3D11Device from slot 37, IDXGIObject-based from slot 5, ID3D11DeviceChild-based (context, resources…) from slot 7. Evidence: in each vtable, two adjacent slots have the SetPrivateDataInterface shape (GUID, pointer) and every later slot matches the desktop method one position earlier (device: slot 38 returns 0xB100 = GetFeatureLevel, 39 returns a field = GetCreationFlags, 24 and 25 share code = CreateQuery/CreatePredicate, 28 returns E_NOTIMPL = OpenSharedResource, 33 switches on the feature enum = CheckFeatureSupport). What the extra method does is unknown (it uses the same private-data store).

**ID3D11DeviceX**: 84 slots, vtable at 0x16f2e0 (in `.data`), installed by `UMDCreateDevice` (0x2c770). Slots 0–53 = desktop ID3D11Device2 order with the +1 shift from 37 (so 0–54 used). Slots 55–83 are Xbox-only. Slot 55 uses the same function as GetImmediateContext (→ "GetImmediateContextX"). Several Xbox slots return E_NOTIMPL. `src/hle/d3d11x/desktop_slots.h` (generated) has the desktop numbers.
- **Slot 59** (umd 0x2b2b0 → 0x27ed0) creates a 0xA8-byte device child with a **30-slot vtable at 0x16f580**: `(const desc*, out**)`. Desc: `+0 u32` flags whose low 4 bits pick an engine (the game passes 1 and 2), `+4 u32` ring size (game 0x10000, 0 means 0x80000), `+8 u32` 0. The game creates two at game rva 0x10d8afb / 0x10d8b3d and keeps them at renderer+0x120 / +0x128. The object's slot 8 returns 2, slots 19–25 take 64-bit GPU virtual addresses and reject anything ≥ 1<<40. **Probably the DMA/copy-engine contexts (name unverified).** This is the first unimplemented slot the game hits.

**IDXGIDevice (Xbox)**: 18 slots at 0x16f6c0 = desktop IDXGIDevice2 (17) + the extra slot 5. Slot 8 = GetAdapter (the game calls it at game rva 0x10d8980). Slots 9–17 return DXGI_ERROR_UNSUPPORTED (0x887A0004). IDXGIAdapter slot 8 = EnumOutputs (game passes `(0, &out)` at game rva 0x10d89a2, keeps the output at renderer+0x28).

**Xbox-only IIDs** (umd QueryInterface returns the object itself for each):
- `{88671610-712E-4F1E-84AB-01B5948BD373}` on the device (umd 0x28627). We call it ID3D11DeviceX. The game QIs for it and keeps it at renderer+0x18, then calls slot 59 on it.
- `{9458FE06-C78D-47F7-96A0-EC7B727BE1E9}` on the context (umd context QI 0x8c33, checked first): probably ID3D11DeviceContextX.
- `{48800095-7134-4BE7-9186-B86BECB26477}` on the context (umd generic QI 0x336f). Identity unknown. The game keeps it at renderer+0x30 and does not null-check it.

**The immediate context is a memory block the game pokes directly.**
- umd's context constructor (0x266e0 / 0x267f0) **copies the 0x828-byte (261-slot) method table from 0xd6950 into the context at +0x3D0** and sets the context's vptr to context+0x3D0. (The vtable scanner shows the source as 253 slots: the last 8 entries aren't code pointers.) It also stores 1 at +0x8. AddRef/Release forward to the device's refcount through the device pointer at +0x10.
- **The game inlines context methods.** 54 inlined sites read the byte at **context+0x390**: if **bit 1** is set they call through the embedded table (`call [ctx + 0x3D0 + 8*slot]`), otherwise they write state into the block themselves. Example, game rva 0xc56060: IASetInputLayout inline stores the layout at ctx+0x178 and ORs 0x89 into ctx+0x168 (the dirty flags), or calls ctx+0x460 = slot 18. umd's slot 18 does the same writes.
- **Some inlined writes are not guarded by the bit**: e.g. game rva 0xc5b74e, 0x10c3fa6, 0x10de370 store a packed 64-bit value (0x3FFC0009E00 / 0x9FFC0009E00) at ctx+0x170 and OR 0x46 into ctx+0x168. Our draw code will have to read those fields. Meaning unknown.
- **Context slot map (verified across all 261 slots in umd, 2026-10-24):** 0–6 IUnknown/DeviceChild like desktop, **7 = the extra base slot**, **8–24 = desktop 7–23 (+1)**, **desktop 24 IASetPrimitiveTopology has NO slot** (the game always inlines it, see below), **25–143 = desktop 25–143 exactly** (checked e.g. 83 IAGetPrimitiveTopology writes a dword, 72/77/81/100/104/109 have the constant-buffer-getter shape, 112/113 GetType/GetContextFlags return 0, 114 FinishCommandList E_NOTIMPL on the immediate context, 115/116 reuse the CopySubresourceRegion/UpdateSubresource code). **144–260 are Xbox-only.** `ctx_slot()` in d3d11x.h encodes this. Exception: **slot 20 (index buffer) has an Xbox signature** `(this, hw index type (0 = 16-bit, 1 = 32-bit), buffer, offset)`.
- **The inlined IASetPrimitiveTopology** stores `table[topology]` (a u64) at ctx+0x170 and ORs 0x46 into ctx+0x168, where `table` is a 65-entry u64 array in the game image at **game rva 0x1df87e0** (bits 41+ = GCN primitive type). We read that table at run time to map the value back (context.cpp `apply_inline_state`, called before every draw).
- **Byte ctx+0x390 has two mode bits the inlined code checks:** bit 1 (55 sites): inlined state setters call the table instead of writing fields. **Bit 0 (37 sites): the game writes raw command-buffer packets itself** at ctx+0x50 (write pointer, limit +0x58, slot 208 = "make room"); with bit 0 set it instead calls **slot 209 with compact commands**: 20 bytes each, `u32 op` (bit 31 bind, bits 28–30 kind 0 SRV / 1 CB / 2 sampler, bits 16–19 stage 0 VS 1 HS 2 DS 3 GS 4 PS 5 CS, bits 8–15 slot, byte 0 = 1), `u64 object`, `u64 extra` (0 everywhere seen). Evidence: register bases match umd's GS setters (CB 0x569 = slot 23, sampler 0x67d = slot 32, SRV 0x57d0 = slot 31). We set both bits.

- **The Xbox draw calls pack argument pairs into 64-bit registers** (umd slots 13/21/22 split them with `shr 32` into the DRAW_INDEX_OFFSET_2 / NUM_INSTANCES packets; game call site rva 0xfd9ca5 builds `count << 32`): **13 DrawIndexed(u64 start index | index count << 32, INT base vertex)**, 14 Draw(count, start vertex) = desktop, **21 DrawIndexedInstanced(u64 start index | count << 32, u64 base vertex | start instance << 32, UINT instances)**, **22 DrawInstanced(UINT count, u64 start vertex | start instance << 32, UINT instances)**. ### 3.2 Texture layouts (xg_x) and tiling (verified 2026-10-24)

- **Assets are stored pre-tiled.** `.swatchbin` textures (`burG` container: `BCXT`/`HCXT` chunks; header at +0x40: u16 width, height, depth, …, u8 mip count, format code) decode to scrambled 128-pixel column blocks as linear data.
- **The console GPU tiling:** GB_TILE_MODE0–31 and GB_MACROTILE_MODE0–15 tables at xg_x.dll rva 0x16648 / 0x166c8 (standard GCN 1.1 4-pipe P4_16x16 values; listed in src/hle/xg/gcn.cpp), pipe interleave 256 B and DRAM row 2 KB (xg code at rva 0x6559/0x6560). With AMD addrlib (Mesa, MIT) configured this way (`GB_ADDR_CONFIG = 0x10001002`, family CI), our layouts match the console's XG **exactly** for real assets (tests/gcn_layout_test.cpp: 4/4 sizes, incl. full mip chains — every level is padded to a power of two), and the untiler turns a real BC4 texture into the correct image (tools/swatch_view.cpp).
- **XGComputeOptimalTileMode** (xg rva 0x12f0 → 0x4140), reimplemented in xg.cpp: buffers 0x1F, depth binds → -1, 1D → 8 (linear aligned), 3D → 13, 2D with MiscFlags bit 27 → 16/17 (PRT), else 14 if width/height reach a minimum from a 7-entry table (rva 0x14b58) indexed by log2(min(clamp(2·bpe·64, 256, 2048), bpe·64·samples)) − 6, otherwise 13. **XGComputeOptimalDepthStencilTileModes**: depth = stencil = {1 sample: 0, 2/4: 1, 8: 2}.
- **XG_TEXTURE2D_DESC** = Xbox D3D11 desc (0x34) + TileMode + Pitch (1D/3D the same pattern). **XG_RESOURCE_LAYOUT** is 0xd40 bytes: u64 size, u64 alignment, u32 mips, u32 planes, 3 × 0x460-byte planes {u32 usage, u64 size, u64 base offset, u64 alignment, u32 bytes per element @+0x20, 15 × 0x48-byte mips {u64 size, u64 offset @+8, u64 slice size @+0x10, pitch px, pitch bytes @+0x1c, …, width/height/depth in elements @+0x30/34/38, samples, tile mode}}. Evidence: xg's GetResourceLayout copies 0xd40 bytes; xg's methods read +0x08, +0x30–0x38, plane+0x20; the game's untile loop (rva 0x10c3860) uses the same fields. The XG "texture address computer" is NOT COM: 0 AddRef, 1 Release, 2 GetResourceLayout, 3 GetMipLevelOffsetBytes(plane, mip), 4 GetTexelElementOffsetBytes(plane, mip, x, y, z, sample) (vtable rva 0x14670).
- **Plane usages and metadata planes (2026-10-26, xg_x 2D builder rva 0x1770, DB setup rva 0x59c0, plane finaliser rva 0x2600; decompiled in research/private/xg_decomp):** usage 1 colour/default, 2 CMASK, 3 FMASK, **4 HTILE**, 5/6 the two planes of a two-plane format not bound as depth, **7 depth, 8 stencil**. A 2D texture with 1 mip and bind DEPTH_STENCIL (and not RENDER_TARGET) gets [HTILE] DEPTH [STENCIL]: HTILE unless misc bits 20 and 21 are both set (no depth / no stencil compression, our names), alignment 0x800, size = 4 bytes per 8×8 tile of the padded surface after aligning it to 128×64 (one slice of ≤ 2M pixels) or 512×512, rounded up to 16 KiB. A 1-mip RENDER_TARGET gets colour + CMASK (+ FMASK with MSAA), **not modelled yet** (STUB). Each plane's base offset is the previous plane's *unaligned* end; the running end is aligned to the plane's alignment before adding its size; layout size = final end. The game reads usage 4 and 7 planes to DMA-clear depth targets (rva 0x1150044 stores offset/size; rva 0x1131b85 fills HTILE with 0xffffffff and depth with 1.0f). Our old layout (usage 2 for depth, no HTILE) left those fields unset and the game filled 0xff000000 bytes over thread stacks.
- **Streamed textures:** the game reserves a whole mipmapped texture (VirtualAlloc type 0x30002000) and commits only the tail holding the small mips (e.g. 0x160000 reserved, top 0x60000 committed), clamping LOD until the big mips stream in. Uploads must skip uncommitted mips (placement.cpp, gpumem::readable).


### 3.3 Unified memory (our design)

Placement resources live in game memory; DXVK resources don't. `src/hle/d3d11x/gpumem.*` write-protects uploaded pages; the first write faults, the fault hook (loader/crash.h) marks the page dirty and unprotects. Binding a placement resource uploads it if dirty (buffers: UpdateSubresource; textures: untile each mip/slice). Syscalls into protected pages fail with EFAULT instead of faulting, so `ReadFile` calls `gpumem::prepare_write` first. Render targets/depth/UAVs are GPU-owned and never uploaded. Map on a placement buffer returns the game memory itself.

## 4. Audio

- **FMOD Studio** is statically linked (FMOD C++ symbols in the exe). Banks are `media/audio/**/*.bank`, RIFF `FEV ` format (740 files).
- **FMOD output (verified 2026-10-25):** `MediaDevice::GetDefaultAudioRenderId` (IMediaDeviceStatics S+4, game rva 0x1a62690) → `ActivateAudioInterfaceAsync(id, IID_IAudioClient2, null, handler, &op)` (rva 0x1a62910) → waits for the handler, `op->GetActivateResult` (slot 3), QI for IAudioClient2. Initialize: 48 kHz float stereo, 960-frame buffer, event driven. The Xbox-only hardware-channels interface on the enumerator also has slot 10 = unregister (called from the `HardwareChannelCount` destructor, rva 0xff7640).
- **XMA through SHAPE (AcpHal, verified 2026-10-25 from AcpHal.dll + FMOD's code at rva 0x19d47a0/0x19d4f40):**
  - `ApuCreateHeap(cached bytes, non-cached bytes)` (game: 5 MB, 256 KB); `ApuAlloc(void** va, u32* apu, size, align, flags)` flags 1 = cached heap, 2 = non-cached; `ApuMapVirtualAddress(va) -> u32`, `ApuMapApuAddress(u32) -> va`, `ApuIsVirtualAddressValid(va, access)`.
  - `AcpHalAllocateShapeContexts(SHAPE_CONTEXTS*)`, 0x60 bytes: six counts (SRC, EQ/comp, filter/volume, DMA, XMA, PCM), six array pointers, six APU addresses. Element sizes 32/160/32/16/64/32; XMA ≤ 0x200, PCM ≤ 0xE00, others ≤ 0x1000; numSrc must equal numXma + numPcm. FMOD asks for 512 SRC, 1024 DMA, 512 XMA.
  - `AcpHalCreate(IAcpHal**)`. IAcpHal (not COM): 0 Connect(cmd entries, msg entries), 1 Disconnect, 2 SubmitCommand(type 1..0x1b, u64 context, u32 id, const void* payload, u32 arg), 3 PopMessage(24-byte msg) -> bool, 4 GetNumMessages, 5 Release, 6–9 return 0x8AC80F0E, 10 deleting dtor. Commands are 256-byte queue records; payload sizes per type: 1/0x15–0x1b 16 B, 2/3/5/7 4 B, 4 none, 6/8 64 B, 9–0xe 12 B, 0xf–0x12 8 B, 0x13 24 B, 0x14 112 B.
  - FMOD's protocol: command 2 = message mask (FMOD sends 0xfe); command 1 = run a SHAPE flowgraph `{u32 numCommands, u32 flowgraphApu, u64}`; FMOD keeps 4 credits and gets one back per **message type 2** (flowgraph done). Message 0x10 carries a 64-bit frame counter; 4/8/0x20/0x40/0x80 are errors it logs.
  - Our ACP (src/hle/acphal/acphal.cpp) runs one flowgraph per 128-sample frame and acknowledges it, but doesn't execute SHAPE commands yet (XMA voices are silent). Azimuth decodes XMA with a modified FFmpeg (its licenses.txt).

## 4g. Xbox Live while offline (2026-10-25)

- `User::GetTokenAndSignatureAsync` (IUser S+10..S+12) is answered the way Azimuth answers it: an `IAsyncOperation<GetTokenAndSignatureResult>` that fails with 0x800704CF (network unreachable). `NetworkInformation::GetInternetConnectionProfile` returns null (Azimuth does the same, its "Live table" fixed answer for INetworkInformationStatics slot 7).
- After the title screen's A press the game sends three requests: gameservices.FH2.forzamotorsport.net, music.xboxlive.com (both failures handled) and **sessiondirectory.xboxlive.com …/sessions?…private=true** (Microsoft.Xbox.Services MultiplayerService). The last is waited on by the game job at rva 0x1839500 (run by the job runner at 0x1837940 on a worker thread, scheduled by 0x183bed0) with `task.get()` outside any try block (ppltasks `_Task_impl_base::_Wait` at 0x306810 rethrows the stored exception; its catch handlers only cover the wait), so the failure is fatal. The job skips the query and records 0x4cd if the profile's Live context (CGamerProfile+0x58, created only for non-guest users, rva 0x124b5b0) is null.
- **Resolved 2026-10-25: the failure is meant to be caught.** The job's `.then` is a *task-based* continuation (`_ContinuationTaskHandle<…, std::integral_constant<bool,1>, _TypeSelectorNoAsync>`, ctor rva 0x182d7d0) whose lambda (rva 0x1833dc0) calls `t.get()` inside `catch (Platform::COMException^)` and turns the error into a result code; the session poller (rva 0x183deb0) then retries every 30 s. It escaped only because our runtime threw C++/CX exceptions with their static type (§5a). Offline, every token request fails with 0x800704CF, as in Azimuth.

## 5a. C++ runtime layouts (verified from game code)

- `Concurrency::concurrent_queue<T>` base `_Concurrent_queue_base_v4`: `{vfptr, rep*, items_per_page @0x10, item_size @0x18}`. The derived vtable is `0 _Move_item(page&, idx, src)`, `1 _Copy_item`, `2 _Assign_and_destroy_item(dst, page&, idx)`, `3 scalar deleting dtor`, `4 _Allocate_page()`, `5 _Deallocate_page(page*)`. A page is a 16-byte header followed by items (`item = page + 16 + idx*item_size`). Verified by disassembling the vtable at rva 0x2c66210.
- **PPL tasks (from the reference msvcr110, 2026-10-25):** `_RefCounter {vfptr: 0 deleting dtor, 1 _Destroy; long refs @8}`. `_CancellationTokenState`: state flag @+0x10 (0 none, 1 canceling, 2 canceled; inlined `_IsCanceled` reads it), allocated 0x80 by `_NewTokenState`; `(token*)2` is `_None()`. `_AsyncTaskCollection` 0xf8 with the `_TaskCollection` at +0x10 (the inlined `_ScheduleWithAutoInline` calls `_Schedule/_RunAndWait/_Cancel` on this+0x10 and `_Reference()`s first; the collection's completion does the matching `_Release()`). `_UnrealizedChore`: vfptr (0 = deleting dtor), TaskProc @+8, owning collection @+0x10 (scheduling twice is an error), chore wrapper @+0x18, runtime-owns-lifetime byte @+0x20. ConcRT runs chores inside a catch-all; we do the same with `seh::guarded_call`.
- **C++/CX exceptions carry their dynamic type** (reference msvcr110 `_CxxThrowException` rva 0x47458, vccorlib110 `Exception(int)` rva 0x18088 / `COMException(int)` rva 0x18470): a ThrowInfo with attribute 0x10 (TI_IsWinRT) is only the hat's static type; the real ThrowInfo is in the object's WINRTEXCEPTIONINFO, embedded at object+0x20 (hr +0x40, ThrowInfo +0x50, size 0x40 at +0x58) and pointed to by the word at object−8; `_CxxThrowException` reads `(*(obj−8))+0x30`. `Heap::AllocateException(n)` allocates n+0x10 and returns +0x10 (rva 0x1aa4c). PPL's `_RethrowUserException` (game rva 0x305c70) throws through a `Platform::Exception^` variable, so without this rule `catch (COMException^)` never matches.
- C++/CX boxed values: the ctor stores `GetIBoxVtable(this)` / `GetIBoxArrayVtable(this)` at `this+8`, replacing the compiler's IPropertyValue vtable (seen at rva 0x1986b98).

## 5b. Memory, audio and misc facts (2026-10-25)

- **XMemAlloc attributes** (decoded by the game's own error message at rva 0x125d850): dwObjectType bits 0–13, dwPageSize bits 14–15, dwAllocatorId bits 16–23, dwAlignment bits 24–28, dwMemoryType bits 29–32.
- The game's `operator new` (rva 0x3229c0) allocates from per-category heaps; the category is the u16 at TLS+0x124 (0x902 = audio), and a budget table at rva 0x354fe10+0x10a070 (0x28 per category, enforced when byte +0x10a3f6 has bit 4) can refuse fallback allocations.
- **`mmdevapi!SetWasapiThreadAffinityMask(mask)` returns the previous mask** (the process mask the first time), 0 + ERROR_INVALID_PARAMETER for a mask outside the process's (reference MMDevAPI.dll rva 0x81f0). FMOD's WASAPI output treats 0 as failure; the game then replaces AudioEngineFmod (vtable rva 0x2e73898) with the silent AudioEngineCommon (0x2e733e0, chosen in rva 0x140f68fb0 when slot 0 Init fails), whose slot 84 returns an empty shared_ptr that the world load dereferences (rva 0x100f896).
- IPackageTransferManager S+0 (IIterable<uint32> chunks, enum): install-order request; fully installed → S_OK (game rva 0x11d0b1a).
- Context slots 156–159 (Remap*Inheritance) are `ret 0` in umd: no-ops.
- XG `Slice2DSizeBytes` of a 3D texture is one depth slice (addrlib's `sliceSize` is the whole level): the game fills its 8×8×16 R8G8 linear (tile 8) colour LUT by `z × Slice2DSizeBytes` (rva 0x13b38c0).
- **Install chunks and the title screen (2026-10-25).** The game keeps a set of installed chunks (rva 0x36613f0) fed by `IsChunkInstalled` answers (rva 0x11d0370), `AreChunksInstalled` (rva 0x11cf000) and the whole-package PackageTransferWatcher's **ChunkCompleted** events (handler rva 0x11ceaa0 reads `args.ChunkId`, IChunkCompletedEventArgs {C1B7DCCE-…} S+0). The FMOD bank loader `AudioContentBankFmod::Load` (rva 0x1012110) only consults that set (rva 0x11d0470) for the chunk `CFileSys` maps the bank to (slot 36, rva 0x11f3fe0): `MasterBank.bank` → chunk 0x6df, `MasterBank.strings.bank` 0x6e9, radio Tracks 0x711/0x71b… Chunk 0 means "no chunk" in the file-open paths (rva 0x11e7cb0/0x11f6780/0x11f9960 skip it). The package's chunk list is in `Mount/hash.manifest`: 12-byte records from offset 8, first u32 = chunk id, ids ≥ 0x3fffffff aren't content chunks (1394 chunks; Azimuth builds its set this way). We report every listed chunk as completed when the game subscribes to a whole-package watcher (it does at ~0.5 s); without that no bank loads.
- **Why the title waited:** after the logo parade the title (rva 0x1413250) starts only when the `Splash` (vtable rva 0x2e533c8) slot 154 returns its "finished" byte (+0x44c). That byte is set by the Splash's audio-event handler (rva 0xe93140, event 0x10/4) when the mixer snapshot **`BASE_PressStartMusic`** (/MasterMixer/Snapshots/BaseSnapshots, AudioSnapshotInfo.xml) reports started, which needs MasterBank. With the silent AudioEngineCommon the event is answered at once.
- **Context slot 154 InsertFence(flags) → u64** (game rva 0x1131b65 tracks it at rva 0x10cedb0); we return a counter.
- **DMA engine context** (device slot 59 object, umd vtable 0x16f580). Azimuth's vtable filler (rva 0x101650, interface 6) fills exactly slots 3, 8, 9, 10, 16, 17, 18, 19, 22, 24, so those are the ones the game uses. 9 CopyResource(dst, src, flags 0), 10 CopySubresourceRegion(desktop args + flags 0) (Azimuth strings "DMA CopyResource flags=" etc.), 19 WriteStatus(u64 address, 4-aligned): writes the u32 HRESULT of the last LZ decompression ("DMA status"), **24 LZDecompressMemory(dst, src, u32 src_bytes, u32 flags 0)**: the source is a **zlib stream** (Azimuth rva 0x1483a0 checks the RFC 1950 header, inflates bytes 2..n-4 with libdeflate and compares the big-endian Adler-32; status 0, 0x8007000D bad data, 0x80070017 checksum); output length comes from the stream. 25 = 24 with mode 1 in umd (unused). 16 InsertFence(flags) → u64 (umd 0x8f8d0 gets the fence via 0x8e2c0 and kicks off via 0x8e380 unless flags bit 0; the game's call returns to rva 0x1131bcc, just after the fill), 17 InsertWaitOnFence(flags, u64 fence) (fence bits 48–55 = engine), 18 kickoff (HRESULT), 21 CopyMemoryToMemory(dst, src, bytes), 22 FillMemoryWithValue(dst, bytes, u32) in dwords, 24/25 decompression variants, 26 writes a 3-dword packet 0x20d with an address (unidentified). GPU address = CPU address of title memory, so we run copies/fills synchronously on the CPU (skipping GPU-only memory the CPU never committed); Azimuth names them DmaCopy/DmaFill/DmaDecompression.
- The game uses the D3D immediate context from more than one thread (render thread draws while the main thread clears/copies; `FL_LOG=ctxthreads`). On Azimuth, immediate-context calls from any thread append to one call stream applied by a worker; we turn on DXVK's per-call lock (ID3D10Multithread).

- **Device slots 60/61** (Azimuth names): IsFencePending(u64 fence) / IsResourcePending(resource) → BOOL; the game spins on them (rva 0x10d7dda after DMA LZ work, rva 0x114fee9). **Context slot 240** SetResourceCompression(resource, flags): umd 0x17ec0 rewrites DCC/HTILE enables; the game passes 0 while loading (rva 0x11420a3); a no-op for us.
- **Deferred contexts as draw bundles (2026-10-26):** the game creates deferred contexts with flags 0x60000 and 0xa0000; Azimuth (rva 0x128ff0) accepts only 0, 0x60000, 0xa0000 and treats **bit 17 (0x20000) as a draw bundle** (separate vtable, rva 0x102690). Executing a bundle (rva 0x12c540) requires restore=FALSE and replays it on the executing context's current state: bundles **inherit** render targets, viewports etc. The game's 3D frame (≈870 draws, most in bundles) sets no render target or viewport inside the bundles (trace: viewport 0x0), so on DXVK's plain deferred contexts nothing is rasterised: the 3D scene after the intro is black. Implemented 2026-10-26 by a DXVK patch (below).
- **Bundle inheritance on DXVK (2026-10-26):** with the bundle patch (tools/dxvk-patches) the game's ~600 bundles per frame run on the immediate context's state; the main pass executes them with RT0 + RT1 (1920x1080 R11G11B10) and a D16 depth bound by the immediate context. Bundles are recorded once and replayed (none are recorded in a steady-state frame).
- **ESRAM fields:** the two u32 after the desktop D3D11 descriptor (CreateTexture2D/Buffer) are the ESRAM offset and an ESRAM byte budget (e.g. 1920x1080 tonemap target 0x0+0x800000, scene 0xdd0000+0x800000, depth 0x17e0000+0x820000; small targets use 0x1000000 budgets larger than themselves). Many targets share offsets (time-aliased). We ignore them: each is its own DXVK texture.
- **Post-processing chain (frame trace, 2026-10-26):** MSAA forward/sky pass → resolve/composite into ESRAM 0xdd0000 (bright) → compute luminance (60x34 tiles, 1x1 average ≈ 0.56) and 480x270 downsample → depth-based 480x270 chain and bloom pyramid (black) → 16³ LUT build (compute 2x2x16) → tonemap (PS: motion blur from t3/t6, car layer `color*t9+t8` gated by D16 t10 and main depth t11, bloom add, exposure = VS TexCoord1.w = exp2(lerp of cb1 c6 by luminance between c5 thresholds + c3.w), filmic curve from cb1 c2/c4 divided by its white value, LUT with cb1 c552 = (1/32, 15/16, enable), vignette c8-c13) → copy to the back buffer. Full-screen passes use a 3-vertex buffer (pos float4 + uv float2) with the default rasterizer state.
- **Movies:** after the title the game plays media/UI/Videos/Anthem_Tone_Video.bk2 (195 MB, ~75 s); press_start.bk2 is the title background, T10_MS_Combined.bk2 the boot logos.

## 6. Azimuth vs us: why theirs runs (2026-10-25)

Read from Azimuth's strings and decompiles (Rule 1: behaviour only). Its stack: D3D11.X → Azimuth's own D3D12 layer → D3D12 / vkd3d-proton → Vulkan ("graphics vkd3d-proton shader cache …").

| Area | Azimuth | Us |
|---|---|---|
| Title graphics memory | One contiguous reservation of placeholders (`VirtualAlloc2` + `MapViewOfFile3` over a section), so the memory can be opened as a GPU heap; tracks commits/releases ("a release of title memory", "withdraw the heaps over title memory") | Plain mmap/heap memory; XMemAllocDefault now gets dedicated mappings (was the C heap) |
| Placement buffers | **Zero copy**: `ID3D12Device3::OpenExistingHeapFromAddress` (device slot 48, rva 0x1401504d0) opens a D3D12 heap over the game's memory and places the buffer in it ("D3D12 heap/buffer over title memory"). CPU writes reach the GPU and GPU writes reach the CPU, like an Xbox | A separate DXVK buffer, copied on bind when page tracking says dirty; GPU writes never come back to the CPU |
| Change detection for what must be copied (tiled textures) | OS **write watch** (`GetWriteWatch`, "WriteSeal/WriteUnseal"); if the host refuses, **compare contents** before uploading ("placement uploads compare contents", rva 0x140121930) | Since 2026-10-25 the same idea: userfaultfd write-protect in async mode + `PAGEMAP_SCAN` (gpumem.cpp; works unprivileged with UFFD_USER_MODE_ONLY). Replaced the mprotect + SIGSEGV hook, whose EFAULT/race/decommit problems caused most of that day's crashes |
| ESRAM | Real shared backing; `D3DMapEsramMemory` maps views of it, so aliased mappings of the same pages see the same data | Pages made RW, aliasing ignored |
| Audio | Executes SHAPE flowgraphs (SRC, XMA, DMA…), decodes **XMA2 with a pinned FFmpeg** ("Pinned FFmpeg lacks XMA2 decoder") | Flowgraphs acknowledged, nothing executed: XMA voices are silent and never progress |
| Immediate context | Calls from any thread append to one call stream, applied by a worker thread | DXVK per-call lock |
| Offline Live | Token requests fail with 0x800704CF; privilege checks Restricted; offline secure template from the manifest | Same (since 2026-10-25), no SecureDeviceAssociationTemplate yet |

Linux equivalents of the two big missing pieces: **VK_EXT_external_memory_host** (RADV supports it; vkd3d-proton uses it to implement `OpenExistingHeapFromAddress`) gives zero-copy GPU access to the game's memory; **userfaultfd write-protect in async mode + `PAGEMAP_SCAN`** (the kernel interface Wine uses for `GetWriteWatch`), or content comparison, replaces the mprotect fault hook.
